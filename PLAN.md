# План доведения версии 2.0

Соглашениям больше года, версия 2.0 не выпущена. План делит работу на два прохода:

1. **Проход по разделам.** Автор идет по файлам сверху вниз, в порядке карты разделов README, и пишет, что поменять. Claude оценивает каждое примечание и вносит правку. Все, что нельзя закрыть сразу, уходит в [очередь вопросов](#очередь-вопросов) с меткой, и проход идет дальше.
2. **Закрытие вопросов.** После прохода закрываем очередь по меткам: сверка с PIX, решения, скриншоты, уровни, чек-лист ревьюера.

Затем все изменения сливаются одной веткой и выходит релиз.

## Цель версии 2.0

- **Понятно разработчику любого уровня.** Новичок понимает правило без вопросов: термин есть в глоссарии, есть пример из PIX Studio. Опытный находит нужное правило по заголовку за минуту
- **Основа для ревью.** Ревьюер ссылается на правило по тегу («нарушено ERROR-03»), а 🔴 правило проверяется по коду без спора о вкусах
- **Актуально.** Правила описывают PIX Studio 3.2.1 и выше и текущее состояние внешних систем (Exchange Online, лицензии библиотек)

## Как работать по плану

- **Ветка.** Вся работа идет в одной ветке от `review/v2`, по коммиту на файл. В `docsv2` и `master` ветка сливается в конце, на [этапе 3](#этап-3-релиз-20)
- **Одно примечание автора, одна оценка.** На каждое примечание Claude отвечает, как это согласуется с практикой RPA-сообщества (REFramework UiPath, Blue Prism, Automation Anywhere, PIX), и стоит ли пункт отдельного правила: ✅ совпадает с практикой, ⚠️ спорно, ❌ против практики или лишнее. Затем вносит правку точечно
- **Вопрос не закрывается сразу.** Claude записывает его в [очередь](#очередь-вопросов) с меткой и ссылкой на правило, а файл отмечает пройденным
- **После правок в docs/.** `python tools/build_docs.py`, `python tools/check_links.py`, запись в `CHANGELOG.md`

### Метки

| Метка | Что нужно, чтобы закрыть |
|-------|--------------------------|
| `PIX` | Проверить в PIX Studio или PIX Master: название активности, поведение, настройка |
| `РЕШЕНИЕ` | Решение автора: оставить, убрать, переписать |
| `УРОВЕНЬ` | Пересмотреть уровень правила: 🔴 только если нарушение можно увидеть на ревью и оно блокирует PR |
| `АКТУАЛЬНО` | Факт мог устареть за год: проверить и обновить |
| `ИБ` | Согласовать формулировку со службой информационной безопасности |
| `СКРИН` | Сделать скриншот в PIX Studio вместо C#-вставки или текстового примера |
| `🚧` | Снять плашку «Раздел в работе» или оставить с пояснением |

### Что проверить в каждом файле

- [ ] Смысл и формулировки соответствуют практике команды
- [ ] Новичок поймет правило без вопросов: термины есть в глоссарии, есть «Почему» и пример
- [ ] 🔴 стоит только там, где нарушение видно на ревью и должно блокировать PR
- [ ] Нет выдуманных возможностей PIX RPA и PIX Master, нет устаревших фактов
- [ ] Нет повторов с другими файлами
- [ ] Текст по [правилам стиля](CONTRIBUTING.md#стиль-текста)

Статус файла: `[ ]` не начат, `[~]` идет проход, `[x]` проход завершен (открытые вопросы файла ждут в очереди).

- [ ] `РЕШЕНИЕ` [TEMPLATE-02](docs/1-project/template.md#template-02-используйте-состояния-state-machine-по-назначению), [QUEUE-04](docs/3-integrations/queue.md#queue-04-правильно-обрабатывайте-повторные-попытки-retry): три уровня повторов (запуск, очередь, задача) не зависят друг от друга, поэтому попытки перемножаются: 3 в запуске × 3 в очереди × 2 у задачи дают 18 попыток на элемент. Нужна рекомендация, на каком уровне повторять и какие значения ставить по умолчанию
