# Глоссарий

| Термин | Определение |
|--------|-------------|
| **Ассет** | Параметр робота, который хранится в PIX Master, в разделе **«Данные» (Data)**. Робот получает значение по ключу при запуске. Значение бывает общим или своим для агента. Подробно: [Что такое ассет](1-project/config.md#что-такое-ассет) |
| **Бизнес-исключение** | Ошибка в данных транзакции: робот работает исправно, но обработать транзакцию по правилам процесса не может. Например, контрагента с таким ИНН нет в справочнике. Повтор не поможет. Робот вызывает `PIX.Core.Exceptions.BusinessRuleException` и берет следующую транзакцию. См. [ERROR-06](2-develop/error.md#error-06-разделяйте-бизнес-исключения-и-технические-исключения) |
| **Техническое исключение (системное)** | Любое исключение, кроме бизнес-исключения. Обычно это ошибка окружения: система не отвечает, файл заблокирован, окно не появилось или зависло. Повтор может помочь: для UI разработчик предусматривает повтор действия, без UI повторяется транзакция целиком ([QUEUE-04](3-integrations/queue.md#queue-04-правильно-обрабатывайте-повторные-попытки-retry)). Повтор не должен создавать дублей ([RECOVERY-01](2-develop/recovery.md#recovery-01-делайте-обработку-транзакции-идемпотентной)). См. [ERROR-06](2-develop/error.md#error-06-разделяйте-бизнес-исключения-и-технические-исключения) |
| **Транзакция** | Одна единица работы робота: данные и шаги для их обработки. Транзакции не зависят друг от друга: если одна упала, робот берет следующую. Например, одно письмо, один счет, одна строка реестра |
| **Очередь данных** | Встроенный в PIX Master брокер сообщений: хранит транзакции и выдает их роботам по одной. Кроме очереди мастера, роботы могут работать с внешними брокерами, например RabbitMQ или Kafka. Как устроена очередь мастера: [Об очередях PIX Master](3-integrations/queue.md#об-очередях-pix-master), [документация PIX Master](https://docs.pixrobotics.com/articles/#!rpa/master-queues) |
| **Элемент очереди** | Транзакция, сохраненная в очереди данных PIX Master, со статусом обработки. Поля и статусы описаны в [документации PIX Master](https://docs.pixrobotics.com/articles/#!rpa/master-queues). См. [QUEUE-02](3-integrations/queue.md#queue-02-обрабатывайте-элемент-очереди-как-транзакцию) |
| **Ссылка элемента очереди** (reference) | Дополнительный идентификатор элемента: ключ транзакции из источника, например номер счета, ID письма или номер заявки. Если в очереди включена проверка уникальности ссылок, мастер не добавит второй элемент с той же ссылкой. См. [QUEUE-09](3-integrations/queue.md#queue-09-задавайте-элементу-очереди-уникальную-ссылку) |
| **SLA** (Service Level Agreement) | Согласованный срок, за который работа должна быть выполнена. У элемента очереди PIX Master SLA задается в секундах с момента создания элемента. Если элемент не обработан за это время, мастер отмечает превышение SLA, но обработку не прекращает |
| **Контур** (среда, стенд, environment) | Отдельный набор всего, с чем работает робот: машины, целевые системы и их данные, ассеты в PIX Master. Контуры изолированы: робот на DEV не трогает данные PROD. DEV — разработка, UAT — тестирование и приемка, PROD — работа на реальных данных. Код робота на всех контурах один, различаются значения ассетов ([PUBLISH-02](4-master/publish.md#publish-02-продвигайте-одну-и-ту-же-сборку-по-контурам-dev--uat--prod)) |
| **PIX Master (мастер, оркестратор)** | Серверный компонент PIX RPA для управления роботами, расписаниями, очередями и ассетами |
| **Робот** | Общее название автоматизации процесса. В PIX Master отдельной сущности «робот» нет: робот складывается из проекта, задачи и агента. Фраза «робот упал» обычно значит, что задача завершилась с ошибкой |
| **Проект** | Код робота: скрипты `.pix` и нужные им файлы. Описывает, что делать. В PIX Master загружается архивом, у каждой загрузки своя версия |
| **Скрипт PIX** (`.pix`) | Файл проекта с последовательностью активностей. Проект состоит из стартового скрипта, который указывают при загрузке в PIX Master, и скриптов, которые он вызывает. Скрипт принимает параметры и возвращает результат, как функция. См. [PROJECT-01](1-project/project.md#project-01-разделяйте-проект-на-слои), [PROJECT-07](1-project/project.md#project-07-организуйте-бизнес-логику-транзакции-по-паттерну-transaction-script) |
| **Активность** | Готовое действие в PIX Studio: открыть приложение, нажать кнопку, прочитать Excel, положить элемент в очередь. Из активностей собираются скрипты PIX. Если готовой активности нет, действие пишут на C# |
| **Задача** | Настройка запуска в PIX Master: какой проект и какую его версию запускать, с какими параметрами и на каких агентах. Один запуск задачи — один запуск робота |
| **Очередь задач** | Очередь запусков задач в PIX Master. Не путать с очередью данных: здесь ждут запуски роботов, а не транзакции. Если агент занят, запуск ждет в очереди задач, а не завершается ошибкой. Строгая очередь запускает задачи строго по порядку, гибридная пропускает вперед задачу, которая может выполниться сейчас. Задача без очереди попадает в очередь Default |
| **Cron-выражение** | Строка, которой задают расписание запуска. PIX Master использует формат Quartz: поля идут в порядке секунды, минуты, часы, день месяца, месяц, день недели. Например, `0 0 9 ? * MON-FRI` — в 9:00 по будням |
| **Подписка на событие** | Настройка PIX Master: когда элемент задачи, очереди данных или процесса переходит в выбранный статус, мастер запускает задачу или процесс. Например, в очереди появился элемент в статусе New, и запускается робот-обработчик. См. [QUEUE-12](3-integrations/queue.md#queue-12-запускайте-обработку-очереди-по-событию-и-подстраховывайте-процессом) |
| **Процесс мастера** | Схема из блоков в PIX Master: запуск задач, условия, работа с очередями, почта, ожидание. Связывает несколько задач в цепочку или подстраховывает подписку: проверяет очередь и запускает робота, если в ней есть элементы. Не путать с бизнес-процессом, который автоматизирует робот. См. [QUEUE-12](3-integrations/queue.md#queue-12-запускайте-обработку-очереди-по-событию-и-подстраховывайте-процессом) |
| **Машина** (хост, сервер робота) | Сервер, на котором работают роботы, и его запись в PIX Master. На машине работает несколько агентов, каждый под своей учетной записью. Сколько роботов работает одновременно, зависит от числа одновременных RDP-подключений, разрешенных лицензиями |
| **Агент** | Программа PIX Agent, которая получает задачи от мастера и запускает проект. В PIX Master агент привязан к машине и к учетной записи Windows, под которой он подключается к машине по RDP. Агент выполняет одну задачу за раз |
| **PIX Agent Host Service** | Служба Windows на машине. По команде мастера открывает сессию, запускает агента и после задачи выключает его. Без службы агент — обычная программа: после перезагрузки сервера ее никто не запустит |
| **Unattended-робот** (фоновый робот, агент) | Робот, который работает без участия человека. Запускается мастером по расписанию или по событию и работает на машине в своей сессии. Подходит для процесса целиком: обработка заявок, сверка, загрузка реестров. В PIX Master такой робот работает через агента |
| **Attended-робот** (робот-помощник, ассистент) | Робот, который работает на компьютере сотрудника в его сессии и запускается им по требованию. Берет на себя часть работы сотрудника: заполнить форму, собрать данные по клиенту. Может запросить у человека данные или подтверждение. Обычно запускается через PIX Runner или вызовом `robot.exe` с командами из консоли |
| **PIX Runner** | Приложение сотрудника для работы с роботами в формате чата: каждый робот — отдельный контакт. В чате сотрудник запускает и останавливает робота, получает от него сообщения и отвечает на запросы. Через подключение к PIX Master загружает проекты и запускает задачи мастера |
| **Шаблон проекта** | Готовая структура проекта робота, с которой начинают разработку: папки, состояния, обработка ошибок, логирование, чтение конфигурации. Шаблон выбирают по типу процесса. См. [Другие шаблоны](1-project/project.md#другие-шаблоны) |
| **State Machine** (конечный автомат) | Способ построить шаблон проекта как набор состояний и переходов между ними. В каждый момент робот находится в одном состоянии. После каждого исхода (успех, бизнес-исключение, техническое исключение, данных больше нет) переход заранее определен, поэтому ошибки обрабатываются в одном месте, а робот может восстановиться и продолжить. Самая распространенная схема — четыре состояния Init → Get Transaction → Process Transaction → End Process. См. [PROJECT-02](1-project/project.md#project-02-используйте-шаблон-на-основе-state-machine), [PROJECT-03](1-project/project.md#project-03-используйте-состояния-по-назначению) |
| **REFramework** (Robotic Enterprise Framework) | Шаблон транзакционного робота на State Machine от UiPath, ставший стандартом в RPA. Описывает четыре состояния, разделение бизнес- и технических исключений, повторы и восстановление приложений. Шаблоны PIX построены по той же схеме |
| **Dispatcher / Performer** (поставщик / обработчик, producer / consumer) | Схема, а не шаблон проекта: процесс делится на две стороны, связанные очередью. Dispatcher кладет транзакции в очередь, Performer забирает их по одной и обрабатывает. Поставщиком может быть не только робот, а очередью — не только очередь PIX Master. См. [PROJECT-06](1-project/project.md#project-06-разделяйте-загрузку-и-обработку-транзакций-dispatcher--performer) |
| **Transaction Script** (сценарий транзакции) | Паттерн из DDD и каталога Фаулера: каждая операция системы реализуется своей процедурой от начала до конца. У робота каждый тип транзакции получает свой сценарий: короткий скрипт, который по порядку вызывает шаги, а не один скрипт на сотни активностей. См. [PROJECT-07](1-project/project.md#project-07-организуйте-бизнес-логику-транзакции-по-паттерну-transaction-script) |
| **Идемпотентность** | Свойство операции: если выполнить ее повторно, результат будет тем же, что после первого раза, и ничего не задвоится. Для робота это значит, что повтор транзакции после сбоя не создает второй документ и не отправляет второе письмо. Особенно важно, когда транзакция проходит несколько этапов с сохранением. Пример: робот сначала сохраняет карточку заявки в учетной системе, потом проводит ее. После каждого этапа он ставит метку в элементе очереди: «карточка сохранена», «проведено». Если робот упал после первого этапа, при повторе он видит метку, не создает вторую карточку и сразу переходит к проведению. См. [RECOVERY-01](2-develop/recovery.md#recovery-01-делайте-обработку-транзакции-идемпотентной), [QUEUE-10](3-integrations/queue.md#queue-10-отмечайте-в-элементе-очереди-выполненные-необратимые-шаги) |
| **ТЗ, ЧТЗ** (PDD) | Техническое задание, частное техническое задание: описание процесса с точки зрения бизнеса. Что делает робот, по каким правилам, какие бывают бизнес-исключения |
| **ТП** (SDD) | Технический проект: описание технического решения робота. Архитектура, интеграции, ассеты, очереди и причины выбранных решений |
| **Runbook** (инструкция по сопровождению, руководство администратора, регламент сопровождения) | Инструкция для поддержки: как проверить работу робота и что делать при типовых проблемах |
| **IDP** | Intelligent Document Processing — извлечение данных из документов с помощью OCR и моделей машинного обучения |
| **LLM** | Большая языковая модель |
| **Ручная проверка** (human-in-the-loop) | Проверка результата робота или модели человеком, прежде чем результат пойдет дальше. См. [AI-03](2-develop/ai.md#ai-03-направляйте-неуверенные-результаты-на-проверку-человеку) |
| **API** | Программный интерфейс системы: набор запросов, через которые другая программа читает и меняет данные без пользовательского интерфейса. Например, запрос «создать счет» с данными в JSON вместо заполнения формы. Через API робот работает надежнее и быстрее, чем через UI. См. [INTEGRATION-01](3-integrations/integration.md#integration-01-выбирайте-канал-интеграции-по-надежности-api--бд--файлы--ui) |
| **Селектор** (XPath) | Описание, по которому робот находит элемент интерфейса: кнопку, поле, строку таблицы. Задается свойствами элемента (имя, тип, id) или путем XPath. Хороший селектор опирается на устойчивые свойства и не ломается от мелких изменений интерфейса. См. [UI-01](2-develop/ui.md#ui-01-не-используйте-абсолютные-xpath-пути), [UI-02](2-develop/ui.md#ui-02-ищите-элементы-desktop-ui-по-уникальным-свойствам) |
| **ПДн** (персональные данные) | Любые сведения, по которым можно определить человека: ФИО, телефон, паспорт, адрес, СНИЛС. Их обработку регулирует 152-ФЗ, поэтому робот берет только нужные для задачи данные, не пишет их в логи и не копирует на тестовые контуры. См. [PRIVACY-01](2-develop/privacy.md#privacy-01-обрабатывайте-только-необходимые-персональные-данные) |
| **🔴 Обязательно / 🟡 Рекомендуется / 🟢 По ситуации** | Уровни обязательности правил. См. [README](../README.md#уровни-обязательности) |
