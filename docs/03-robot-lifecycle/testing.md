# Тестирование

Тестирование робота проверяет не только основной сценарий, но и поведение при бизнес-исключениях и сбоях окружения: именно они чаще всего приводят к инцидентам в проде. Слой тестов в структуре проекта описан в [PRJ-01](../01-conventions/project-structure.md#prj-01-разделяйте-проект-на-слои).

## Уровни тестирования

| Уровень | Что проверяет | Где выполняется | Кто выполняет |
|---------|---------------|-----------------|---------------|
| Модульные тесты | Отдельные скрипты слоя Helpers: парсинг, валидация, расчеты | Машина разработчика | Разработчик |
| Интеграционные тесты | Работа слоя Infrastructure с реальными системами | Контур DEV / UAT | Разработчик |
| Сквозные (E2E) тесты | Робот целиком на наборе тестовых транзакций | Контур UAT | Разработчик, аналитик |
| Приемочное тестирование (UAT) | Соответствие PDD на данных, близких к реальным | Контур UAT | Владелец процесса |

## TST-01. Покрывайте тестами скрипты с бизнес-логикой и преобразованием данных

**Уровень:** SHOULD — рекомендуется

Скрипты, которые не зависят от внешних систем (парсинг дат и сумм, валидация реквизитов, маппинг статусов, расчеты), проверяются модульными тестами в слое Tests. Такие тесты выполняются за секунды и ловят регрессии при любом изменении.

- Для каждого скрипта проверяйте основной случай, граничные значения и некорректный ввод
- При исправлении ошибки сначала добавьте тест, который ее воспроизводит

## TST-02. Тестируйте все бизнес-исключения из PDD

**Уровень:** MUST — обязательно

Для каждого бизнес-исключения, перечисленного в PDD, подготовьте тестовую транзакцию и проверьте, что робот:

- определяет ее именно как бизнес-исключение (см. [EXC-06](../01-conventions/exceptions.md#exc-06-разделяйте-бизнес-исключения-и-системные-исключения))
- устанавливает понятный статус элемента очереди (см. [QUE-03](../01-conventions/queues.md#que-03-используйте-информативные-сообщения-в-статусах-очередей))
- переходит к следующей транзакции без повторов

## TST-03. Проверяйте поведение робота при сбоях окружения

**Уровень:** MUST — обязательно

Перед релизом проверьте на контуре UAT хотя бы следующие сценарии:

- [ ] Целевая система недоступна при старте (Init) — робот завершается с понятной ошибкой
- [ ] Целевая система становится недоступна во время обработки — срабатывают повтор и восстановление (см. [Надежность](../01-conventions/reliability.md))
- [ ] Серия системных ошибок — робот останавливается по порогу (см. [REL-05](../01-conventions/reliability.md#rel-05-останавливайте-робота-после-серии-системных-исключений-подряд))
- [ ] Повторная обработка уже обработанной транзакции не создает дубликат (см. [REL-01](../01-conventions/reliability.md#rel-01-делайте-обработку-транзакции-идемпотентной))
- [ ] Сигнал остановки из мастера — робот корректно завершает текущую транзакцию и останавливается
- [ ] Пустая очередь или пустая входная папка — робот штатно завершает работу

## TST-04. Используйте подготовленные и обезличенные тестовые данные

**Уровень:** MUST — обязательно

- Тестовый набор покрывает основной сценарий, все бизнес-исключения и граничные значения
- Тестовые данные обезличены (см. [PD-04](../01-conventions/personal-data.md#pd-04-используйте-обезличенные-данные-для-разработки-и-тестирования))
- Тестовые данные хранятся вместе с проектом или в описанном в README месте, чтобы тесты можно было повторить
- Тест можно выполнить повторно: подготовьте способ вернуть тестовую среду в исходное состояние

[⬆ К содержанию](#содержание)

## TST-05. Фиксируйте приемку результатом UAT

**Уровень:** MUST — обязательно

Приемочное тестирование проводит владелец процесса по сценариям из PDD. Результат оформляется актом или комментарием в задаче: какие сценарии проверены, какие замечания найдены и как они решены. Без подтвержденной приемки робот не выпускается на контур PROD.

[⬆ К содержанию](#содержание)

## TST-06. Проводите регрессионное тестирование при изменениях в целевых системах

**Уровень:** SHOULD — рекомендуется

Обновление целевой системы (новая версия 1С, изменение веб-портала, обновление браузера) может сломать робота без единого изменения в его коде.

- Узнавайте о плановых обновлениях систем заранее: договоритесь с владельцами систем об оповещении
- После обновления прогоните E2E-тесты на контуре UAT до того, как обновление попадет в PROD
- Если обновление уже в PROD, в первый день после него усильте мониторинг робота

## TST-07. Именуйте и структурируйте тесты единообразно

**Уровень:** SHOULD — рекомендуется

**Размещение.** Тесты лежат в слое `Tests` проекта робота (см. [PRJ-01](../01-conventions/project-structure.md#prj-01-разделяйте-проект-на-слои)): модульные — в `Tests/UnitTests`, интеграционные — в `Tests/IntegrationTests`. Структура папок внутри повторяет структуру тестируемых слоев: тест скрипта `Helpers/ParseInvoiceDate` лежит в `Tests/UnitTests/Helpers/`.

**Именование.** Имя теста состоит из трех частей: `{ЧтоТестируем}_{Условие}_{ОжидаемыйРезультат}`.

| Хорошо | Плохо |
|--------|-------|
| `ParseInvoiceDate_DotSeparatedDate_ReturnsDate` | `Test1` |
| `ParseInvoiceDate_EmptyString_ThrowsBusinessException` | `ParseDateTest` |
| `CalculateVat_ZeroAmount_ReturnsZero` | `CheckVat` |

**Структура теста — Arrange / Act / Assert.** Каждый тест состоит из трех блоков: подготовка данных, вызов тестируемого скрипта, проверка результата. Один тест проверяет один сценарий.

```csharp
// Arrange
var input = "15.06.2025";

// Act
var result = ParseInvoiceDate(input);

// Assert
if (result != new DateTime(2025, 6, 15))
    throw new Exception($"Ожидалась дата 15.06.2025, получено {result:dd.MM.yyyy}");
```

**Правила:**
- Тест не зависит от других тестов и порядка запуска
- Модульный тест не обращается к внешним системам, файлам на сетевых дисках и ассетам мастера: все входные данные задаются в самом тесте
- Интеграционные тесты работают только с контурами DEV/UAT: адреса систем берутся из ассетов контура, а не прописываются в тесте
- Тест, который падает, не отключается и не удаляется без задачи на исправление
