# Код-ревью

Код-ревью проверяет, что изменение соответствует соглашениям, решает задачу и не создает новых рисков. Процесс работы с Pull Request описан в [GIT-03](../01-conventions/git.md#git-03-используйте-pullmerge-request-для-изменений); этот раздел описывает, что именно проверять.

## REV-01. Проверяйте изменения по чек-листу

**Уровень:** MUST — обязательно

Ревьюер проходит по [чек-листу код-ревью](../../templates/code-review-checklist.md). Чек-лист собран из правил уровня MUST и типичных ошибок RPA-проектов.

В первую очередь проверяйте то, что сложнее всего исправить после релиза:
1. Конфиденциальные и персональные данные в коде, логах и репозитории
2. Обработка исключений: разделение бизнес- и системных ошибок, отсутствие пустых `catch`
3. Идемпотентность и порядок обновления статуса очереди
4. Жестко закодированные значения, которые должны быть в ассетах
5. Таймауты во всех ожиданиях и внешних вызовах

Стиль и именование проверяйте в последнюю очередь.

## REV-02. Ссылайтесь на правила по идентификатору

**Уровень:** SHOULD — рекомендуется

В комментарии к PR указывайте идентификатор правила: «LOOP-02: нет таймаута у ожидания окна». Это экономит время на объяснения, делает требования единообразными для всех ревьюеров и показывает, какие правила нарушаются чаще всего.

Если замечание не связано ни с одним правилом, но повторяется, это повод предложить новое правило (см. [CONTRIBUTING](../../CONTRIBUTING.md)).

## REV-03. Разделяйте блокирующие и неблокирующие замечания

**Уровень:** SHOULD — рекомендуется

- **Блокирующее** — нарушение правила уровня MUST или ошибка в логике. PR не сливается, пока замечание не исправлено
- **Неблокирующее** — нарушение SHOULD, предложение по улучшению. Помечайте префиксом `nit:` или «необязательно»; автор решает сам, исправлять ли сейчас
