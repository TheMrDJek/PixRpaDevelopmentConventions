# Очереди

Очереди в PIX Master — это мощный инструмент для организации параллельной обработки данных и масштабирования роботов. Правильное использование очередей значительно повышает отказоустойчивость и эффективность автоматизации.

**Основные принципы работы с очередями:**
- Очереди позволяют распределять нагрузку между несколькими экземплярами роботов
- Элементы очереди сохраняют состояние между запусками роботов
- Возможность обработки исключений и повторного запуска проблемных элементов

## Об очередях PIX Master

Очередь данных PIX Master хранит транзакции и выдает их роботам по одной. Элементы кладут роботы, процессы мастера и внешние системы через API. Поля, статусы и настройки подробно описаны в [документации PIX Master](https://docs.pixrobotics.com/). Здесь — то, что из этого нужно разработчику.

**Что можно положить в элемент:**

| Поле | Тип | Для чего |
|------|-----|----------|
| Значение | `string` | Основные данные транзакции, часто JSON |
| Входные данные | `Dictionary<string, object>` | Параметры транзакции по ключам |
| Выходные данные | `Dictionary<string, object>` | Результат обработки и метки прогресса ([QUEUE-10](#queue-10-отмечайте-в-элементе-очереди-выполненные-необратимые-шаги)) |
| Таблица | `DataTable` | Табличные данные: строки реестра, позиции заказа |
| Вложения | Файлы | Документы для обработки: сканы, письма, выгрузки |
| Ссылка | `string` | Ключ транзакции из источника, защита от дублей ([QUEUE-09](#queue-09-задавайте-элементу-очереди-уникальную-ссылку)) |
| Комментарий | `string` | Короткое пояснение для поддержки |

**Как робот проходит элемент.** Активность «Обработать элемент из очереди» берет элемент и переводит его в статус Processing. После обработки «Подтвердить завершение обработки элемента очереди» переводит его в Processed или в Failed с типом ошибки «Бизнес» или «Техническая» ([ERROR-06](../2-develop/error.md#error-06-разделяйте-бизнес-исключения-и-технические-исключения)). Если целевая система временно недоступна, «Отложить элемент очереди» возвращает элемент в New.

**Настройки очереди, от которых зависит код робота:**
- Повторы: «Использовать попытки», число попыток и задержка ([QUEUE-04](#queue-04-правильно-обрабатывайте-повторные-попытки-retry))
- Проверка уникальности ссылок ([QUEUE-09](#queue-09-задавайте-элементу-очереди-уникальную-ссылку))
- Максимальное время ожидания и максимальное время в статусе Processing ([QUEUE-11](#queue-11-ограничивайте-время-элемента-в-статусах-new-и-processing))
- SLA элемента: за сколько секунд с момента создания элемент должен быть обработан

## QUEUE-01. Выбирайте оптимальный формат данных для элементов очереди

🟡 **Рекомендуется**

В PIX Master данные в элементах очереди можно хранить в различных форматах, каждый из которых имеет свои преимущества и ограничения:

1. **Dictionary (C#):**
- **Рекомендуемый формат** для большинства сценариев в PIX RPA
- Подходит для коллекций ключ-значение с простой структурой
- Обеспечивает быстрый и простой доступ к данным по ключу
- Не требует сложной сериализации/десериализации
- Работает "из коробки" без дополнительных библиотек

2. **DataTable (C#):**
- Оптимален для табличных данных с чёткой структурой строк и столбцов
- Удобен для обработки больших наборов однотипных записей
- Предоставляет встроенные методы для фильтрации и обработки данных
- Эффективен при работе с данными из баз данных и Excel
- Хорошо поддерживается стандартными активностями PIX RPA

3. **JSON-строки:**
- Подходит для обмена данными с внешними системами
- Поддерживает текстовое представление данных
- **Ограничения в PIX RPA:**
    - Сложности с парсингом и созданием вложенных структур без пользовательских классов
    - Рекомендуется использовать только для простых структур
    - Для сложных данных предпочтительнее Dictionary или DataTable

**Рекомендации по выбору формата в PIX RPA:**
- Используйте **Dictionary** как основной формат для большинства сценариев
- Применяйте **DataTable** для табличных данных и при работе с Excel/базами данных
- Используйте **JSON** только для простых структур или когда требуется совместимость с внешними системами
- Избегайте сложных вложенных JSON-структур из-за ограничений парсинга в PIX RPA

## QUEUE-02. Обрабатывайте элемент очереди как транзакцию

🔴 **Обязательно**

Каждый элемент очереди обрабатывается как атомарная транзакция. Статус элемента обновляйте в последнюю очередь, после того как все данные сохранены и обработка транзакции полностью завершена (паттерн «Сохранение данных → Обновление очереди»).

**Основные принципы:**
- В случае сбоя вся транзакция откатывается (если возможно) или регистрируется для ручной обработки
- Статус элемента очереди отражает статус всей транзакции

**Рекомендации:**
- В случае сбоя при сохранении данных не помечайте элемент очереди как успешный
- Сохраняйте контрольные точки для сложных многошаговых процессов
- Реализуйте механизм компенсации для отката частично выполненных операций

**Преимущества:**
- Предотвращение потери данных в случае сбоя системы
- Обеспечение целостности данных
- Упрощение восстановления после сбоев

**Последствия несоблюдения:**
- Риск пометить элемент как обработанный до завершения всех связанных операций
- Сложности при восстановлении после сбоев
- Возможность создания дубликатов и потери данных

**Правильный порядок действий:**
1. Получение элемента из очереди (статус "В обработке")
2. Полная обработка данных и сохранение результатов в целевые системы
3. Проверка успешности всех операций
4. Обновление статуса элемента очереди ("Успешно" или "Ошибка")

## QUEUE-03. Используйте информативные сообщения в статусах очередей

🔴 **Обязательно**

Статусы элементов очереди должны содержать краткую, но информативную информацию о состоянии обработки. В случае ошибки добавляйте ключевую информацию об ошибке.

**Пример информативных сообщений:**
- "Счет успешно создан: INV-12345"
- "Ошибка обработки: данные клиента не найдены"
- "Отложено: ожидание подтверждения от системы XYZ"

**Преимущества:**
- Упрощение мониторинга и анализа производительности
- Ускорение диагностики проблем
- Облегчение ручной обработки исключений

**Структура информативного сообщения об ошибке:**
1. Краткое описание ошибки (1-2 слова)
2. Контекст операции
3. Ключевая информация для исправления (если применимо)

**Пример:** "Ошибка API: создание клиента. Код 403: недостаточно прав"

## QUEUE-04. Правильно обрабатывайте повторные попытки (retry)

🔴 **Обязательно**

Механизм повторных попыток позволяет роботам эффективно справляться с временными сбоями.

**Рекомендации:**
- Используйте встроенный механизм повторных попыток в оркестраторе
- Чётко разделяйте временные и постоянные ошибки
- Устанавливайте разумное количество повторных попыток (обычно 3-5)
- Используйте экспоненциальную задержку между попытками

**Временные ошибки (подходят для retry):**
- Сетевые таймауты
- Временная недоступность API
- Блокировки в базе данных
- Кратковременные сбои в работе внешних систем

**Постоянные ошибки (не подходят для retry):**
- Отсутствие необходимых данных
- Неверный формат входных данных
- Ошибки авторизации и доступа
- Логические ошибки в данных

**В PIX Master** повторы настраиваются в очереди: «Использовать попытки», число попыток, задержка между ними и возврат элемента в конец очереди. Мастер возвращает в работу тот же элемент. Не создавайте вместо упавшего элемента новый: у того же элемента остаются ссылка, счетчик попыток и метки прогресса ([QUEUE-10](#queue-10-отмечайте-в-элементе-очереди-выполненные-необратимые-шаги)). Элемент с типом ошибки «Бизнес» мастер не повторяет.

Вручную поддержка повторяет элемент клонированием в интерфейсе мастера. Клон — новый элемент: метки прогресса в него не переносятся, и обработка начнется с начала. Перед клонированием проверьте, что уже сделано в целевой системе.

## QUEUE-05. Именуйте очереди по формату {Проект}_{ТипДанных}_{Назначение}

🔴 **Обязательно**

- Примеры:
  - `AP_Invoices_Processing` — очередь счетов для обработки в проекте Accounts Payable

Если процесс построен по схеме Dispatcher/Performer (см. ## QUEUE-09. Задавайте элементу очереди уникальную ссылку

🔴 **Обязательно** для схемы Dispatcher / Performer

Поставщик может упасть посреди загрузки и после перезапуска положить те же транзакции второй раз. Ссылка элемента защищает от этого: включите в очереди «Проверять уникальность ссылок», и мастер не добавит элемент со ссылкой, которая уже есть.

- В ссылку пишите ключ транзакции из источника: номер счета, ID письма, номер заявки. Если ключа нет, создайте его у поставщика (например, GUID) и сохраните вместе с исходными данными
- Выберите статусы, в которых проверяется уникальность. Для Failed с типом ошибки «Техническая» проверку обычно отключают, чтобы упавшую транзакцию можно было загрузить заново
- Отказ мастера из-за повторной ссылки — не сбой загрузки: поставщик считает такую транзакцию уже загруженной и переходит к следующей
- Ссылка связывает элемент с объектом во внешней системе: по ней поддержка находит транзакцию, а обработчик проверяет, не создан ли уже документ ([RECOVERY-01](../2-develop/recovery.md#recovery-01-делайте-обработку-транзакции-идемпотентной))

## QUEUE-10. Отмечайте в элементе очереди выполненные необратимые шаги

🟡 **Рекомендуется**

Элемент может прийти к обработчику повторно: после технической ошибки, повтора очереди или перезапуска задачи. Если транзакция уже прошла необратимый шаг (документ проведен, платеж отправлен), повтор не должен выполнить его второй раз ([RECOVERY-01](../2-develop/recovery.md#recovery-01-делайте-обработку-транзакции-идемпотентной)).

Сразу после необратимого шага запишите метку в элемент очереди, например в выходные данные. При повторе обработчик проверяет метку и выполняет только оставшиеся шаги.

**Пример.** Робот добавляет позицию в документ 1С и проводит его, затем формирует отчет. После проведения он ставит в элементе метку «проведено». Если робот упадет на отчете, при повторе он увидит метку, пропустит работу с документом и сформирует только отчет.

- Ставьте метку в том же скрипте, который выполняет необратимый шаг, чтобы между шагом и меткой не было других действий
- Метка в элементе очереди переживает падение робота и перезапуск агента и видна поддержке в интерфейсе мастера. Файл на машине робота этого не дает
- При клонировании элемента метки не переносятся ([QUEUE-04](#queue-04-правильно-обрабатывайте-повторные-попытки-retry))

## QUEUE-11. Ограничивайте время элемента в статусах New и Processing

🔴 **Обязательно**

Если робот взял элемент и упал, не подтвердив его, элемент остается в статусе Processing. Без таймаута мастер его больше не выдаст, и транзакция зависнет до ручного разбора.

- Задайте в очереди «Максимальное время обработки элемента очереди в статусе Processing» с запасом над самой долгой нормальной обработкой. По его истечении элемент перейдет в TimeOut
- Задайте «Максимальное время ожидания обработки элемента очереди», если транзакция теряет смысл после срока. Для отдельного элемента используйте «Крайний срок»
- Значение 0 означает, что действует общая настройка PIX Master. Если и там 0, ограничения нет
- В коде робота подтверждайте элемент при любом исходе: и в Process Transaction, и в обработчике ошибок
- Элементы в TimeOut — сигнал, что робот падает, не дойдя до подтверждения. Разбирайте их, а не только упавшие задачи

## QUEUE-12. Запускайте обработку очереди по событию и подстраховывайте процессом

🟡 **Рекомендуется**

Обработчика удобнее запускать по появлению элементов, а не по частому расписанию: робот не стартует впустую, а транзакция начинает обрабатываться сразу. Общий выбор триггера описан в [MASTER-04](../4-master/master.md#master-04-выбирайте-тип-триггера-по-характеру-процесса).

- **Подписка на событие** запускает задачу, когда элемент очереди переходит в нужный статус, например New
- **Процесс мастера** подстраховывает подписку: блок «Кол-во элементов > N» проверяет очередь и, если элементы есть, запускает задачу. Так очередь не встанет, если событие не сработало
- Привяжите задачу к очереди задач: если агент занят, следующий запуск подождет, а не завершится ошибкой
- **Масштабирование:** блок «Распределить для обработки» подключает вторую задачу на другом агенте, когда элементов в очереди больше порога
- Подписки и процессы настраиваются в мастере отдельно от проекта. После переноса на новый контур проверьте, что они созданы и активны
