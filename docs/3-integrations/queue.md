# Очереди

Как робот работает с очередями данных PIX Master: что класть в элемент, как подтверждать и повторять элементы, как называть очереди. Очередь хранит состояние каждой транзакции между запусками, и несколько роботов могут разбирать ее одновременно.

## QUEUE-01. Обрабатывайте элемент очереди как транзакцию

🔴 **Обязательно**

Берите элемент активностью «Обработать элемент из очереди». При получении элемента она переводит его в `Processing` («В обработке»). [Активность получения элемента](https://knowledgebase.pixrpa.ru/actions/queues/getelement)

Записывайте итог активностью «Подтвердить завершение обработки элемента очереди». Указывайте успех (`Processed`) после сохранения результата, как требует [CODE-03](../2-develop/code.md#code-03-подтверждайте-успех-после-сохранения-результата). Если попытка завершилась ошибкой, передайте `false` как результат обработки и укажите тип ошибки по [ERROR-03](../2-develop/error.md#error-03-разделяйте-бизнес-исключения-и-технические-исключения). Если работа должна начаться позже, отложите элемент по [QUEUE-03](#queue-03-правильно-обрабатывайте-повторные-попытки-retry).

Если сбой произошёл после части изменений, выполните предусмотренный для процесса откат. Если робот не может безопасно продолжить или отменить изменения, передайте элемент на ручной разбор. Сведения о выполненных необратимых шагах сохраняйте по [QUEUE-11](#queue-11-отмечайте-в-элементе-очереди-выполненные-необратимые-шаги).

## QUEUE-02. Используйте информативные сообщения в статусах очередей

🔴 **Обязательно**

Статус элемента коротко говорит, что с ним случилось. Если элемент упал, добавьте в статус причину ошибки.

**Пример информативных сообщений:**
- "Счет успешно создан: INV-12345"
- "Ошибка обработки: данные клиента не найдены"
- "Отложено: ожидание подтверждения от системы XYZ"

**Почему:** по статусу поддержка понимает, что случилось с элементом, не открывая лог.

**Структура информативного сообщения об ошибке:**
1. Краткое описание ошибки (1-2 слова)
2. Контекст операции
3. Ключевая информация для исправления (если применимо)

**Пример:** "Ошибка API: создание клиента. Код 403: недостаточно прав"

## QUEUE-03. Правильно обрабатывайте повторные попытки (retry)

🔴 **Обязательно**

Выберите действие по тому, чем закончилась попытка.

| Ситуация | Действие |
|---|---|
| Робот получил ошибку и завершает попытку. Например, 1С вернула ошибку при записи документа | Подтвердите ошибку (`Failed`) и укажите её тип. Техническая ошибка может запустить повтор. [QUEUE-01](#queue-01-обрабатывайте-элемент-очереди-как-транзакцию), [ERROR-03](../2-develop/error.md#error-03-разделяйте-бизнес-исключения-и-технические-исключения) |
| Работу нужно начать позже. Например, выгрузка будет доступна после 18:00 | Вызовите «Отложить элемент очереди» и задайте время в поле «Отложить обработку до». Элемент вернётся в `New`. Мастер выдаст его не раньше указанного времени. После откладывания переходите к следующему элементу. [Активность откладывания](https://knowledgebase.pixrpa.ru/actions/queues/postponeelement), [Переход в New](https://knowledgebase.pixrpa.ru/changelog/studio_3) |

### Повторы в PIX Master

При временном сбое выбирайте один уровень повтора. Учитывайте шаги, которые робот уже выполнил. [RECOVERY-01](../2-develop/recovery.md#recovery-01-делайте-обработку-транзакции-идемпотентной).

- **Повтор в Мастере.** Выберите его, если сервису нужно время на восстановление и элемент можно безопасно обработать снова. Например, API поставщика временно недоступен. Робот делает один вызов за попытку обработки элемента. При таймауте он завершает попытку с `Failed` и типом ошибки «Техническая». В настройках очереди включите «Использовать попытки», задайте число попыток и паузу. Мастер вернёт элемент на обработку, если остались попытки. [Повторные попытки в PIX Master](https://knowledgebase.pixrpa.ru/releasenotes).
- **Повтор в коде.** Выберите его, если достаточно повторить один безопасный вызов и очередь не повторяет элемент после этого сбоя. Например, робот может ещё раз запросить карточку клиента по ID и продолжить текущую обработку. Ограничьте число попыток. [INTEGRATION-01](integration.md#integration-01-задавайте-таймауты-для-всех-внешних-вызовов).

Проверьте также настройки повторов запуска робота и задачи. [TEMPLATE-02](../1-project/template.md#переходы).

## QUEUE-04. Именуйте очереди по формату {Проект}_{ТипДанных}_{Назначение}

🔴 **Обязательно**

- Используйте формат: `{Проект}_{ТипДанных}_{Назначение}`
- Примеры:
  - `AP_Invoices_Processing`: очередь счетов для обработки в проекте Accounts Payable
  - `HR_Employees_Validation`: очередь данных сотрудников для валидации в HR-проекте
  - `Sales_Orders_Confirmation`: очередь заказов для подтверждения в проекте Sales

Если процесс построен по схеме Dispatcher/Performer (см. [справку](../1-project/project.md#когда-делить-решение-на-роботов-dispatcher--performer-и-цепочки)), очередь между ними называется по сущности, которую она содержит, а не по роботу: `AP_Invoices_Processing`, а не `AP_Dispatcher_Queue`.

## QUEUE-06. Задавайте элементу очереди уникальную ссылку

🔴 **Обязательно** для схемы Dispatcher / Performer

Поставщик может упасть посреди загрузки и после перезапуска положить те же транзакции второй раз. Ссылка элемента защищает от этого: включите в очереди «Проверять уникальность ссылок», и мастер не добавит элемент со ссылкой, которая уже есть.

- В ссылку пишите ключ транзакции из источника: номер счета, ID письма, номер заявки. Если ключа нет, создайте его у поставщика (например, GUID) и сохраните вместе с исходными данными
- Выберите статусы, в которых проверяется уникальность. Для Failed с типом ошибки «Техническая» проверку обычно отключают, чтобы упавшую транзакцию можно было загрузить заново
- Если мастер отказал из-за повторной ссылки, загрузка не сломалась: поставщик считает такую транзакцию уже загруженной и переходит к следующей
- Ссылка связывает элемент с объектом во внешней системе: по ней поддержка находит транзакцию, а обработчик проверяет, не создан ли уже документ ([RECOVERY-01](../2-develop/recovery.md#recovery-01-делайте-обработку-транзакции-идемпотентной))

## QUEUE-07. Ограничивайте время элемента в статусах New и Processing

🔴 **Обязательно**

Задайте лимит обработки в `Processing` с запасом над обычной длительностью. Если робот упал до подтверждения, планировщик PIX Master переведёт элемент в `TimeOut` по истечении лимита. Для элементов в `New` задайте срок ожидания, если работа со временем теряет смысл.

Перед ручным повтором проверьте результат по [RECOVERY-01](../2-develop/recovery.md#что-проверить-перед-повтором-в-1с). Клонирование и вызов `RetryTimedOutItem` создают новый элемент в `New`. Исходный остаётся в `TimeOut`. [Схема переходов PIX Master](https://docs.pixrobotics.com/articles/#!rpa/master-queues).

## QUEUE-08. Выбирайте оптимальный формат данных для элементов очереди

🟡 **Рекомендуется**

В PIX Master данные в элементах очереди можно хранить в различных форматах, каждый из которых имеет свои преимущества и ограничения:

1. **Dictionary (C#):**
- **Рекомендуемый формат** для большинства сценариев в PIX RPA
- Подходит для коллекций ключ-значение с простой структурой
- Обеспечивает быстрый и простой доступ к данным по ключу
- Не требует сложной сериализации/десериализации
- Работает "из коробки" без дополнительных библиотек

2. **DataTable (C#):**
- Оптимален для табличных данных с чёткой структурой строк и столбцов
- Удобен для обработки больших наборов однотипных записей
- Предоставляет встроенные методы для фильтрации и обработки данных
- Эффективен при работе с данными из баз данных и Excel
- Хорошо поддерживается стандартными активностями PIX RPA

3. **JSON-строки:**
- Подходит для обмена данными с внешними системами
- Поддерживает текстовое представление данных
- **Ограничения в PIX RPA:**
    - Сложности с парсингом и созданием вложенных структур без пользовательских классов
    - Рекомендуется использовать только для простых структур
    - Для сложных данных предпочтительнее Dictionary или DataTable

**Рекомендации по выбору формата в PIX RPA:**
- Используйте **Dictionary** как основной формат для большинства сценариев
- Применяйте **DataTable** для табличных данных и при работе с Excel/базами данных
- Используйте **JSON** только для простых структур или когда требуется совместимость с внешними системами
- Избегайте сложных вложенных JSON-структур из-за ограничений парсинга в PIX RPA

## QUEUE-09. Разделяйте очереди по назначению

🟡 **Рекомендуется**

- **Транзакционные очереди.** Для основных бизнес-данных, обрабатываемых роботами
  - `{Проект}_{Сущность}_{Статус}`: `Finance_Invoices_New`, `Finance_Invoices_Failed`
- **Служебные очереди.** Для внутреннего взаимодействия роботов
  - `{Проект}_Service_{Назначение}`: `Common_Service_Notifications`
- **Архивные очереди.** Для хранения исторических данных
  - `{Проект}_{Сущность}_Archive_{Период}`: `Finance_Invoices_Archive_2023Q2`

## QUEUE-11. Отмечайте в элементе очереди выполненные необратимые шаги

🟡 **Рекомендуется**

После подтверждения необратимого шага запишите в элемент очереди, что уже сделано. Например, сразу после проведения документа в 1С сохраните ссылку на документ и отметку «проведён» в выходных данных. При повторе по отметке видно, с какого шага продолжать.

Сохраняйте отметку в том же скрипте, который выполняет шаг. Робот может упасть между записью документа и записью отметки. Перед повтором необратимого действия проверьте результат в целевой системе по [RECOVERY-01](../2-develop/recovery.md#recovery-01-делайте-обработку-транзакции-идемпотентной).

## QUEUE-12. Запускайте обработку очереди по событию и подстраховывайте процессом

🟡 **Рекомендуется**

Обработчика удобнее запускать по появлению элементов, а не по частому расписанию: робот не стартует впустую, а транзакция начинает обрабатываться сразу. Общий выбор триггера описан в [MASTER-05](../4-master/master.md#master-05-выбирайте-тип-триггера-по-характеру-процесса).

- **Подписка на событие** запускает задачу, когда элемент очереди переходит в нужный статус, например New
- **Процесс мастера** подстраховывает подписку: блок «Кол-во элементов > N» проверяет очередь и, если элементы есть, запускает задачу. Так очередь не встанет, если событие не сработало
- Привяжите задачу к очереди задач: если агент занят, следующий запуск подождет, а не завершится ошибкой
- **Масштабирование:** блок «Распределить для обработки» подключает вторую задачу на другом агенте, когда элементов в очереди больше порога
- Подписки и процессы настраиваются в мастере отдельно от проекта. После переноса на новый контур проверьте, что они созданы и активны

## Об очередях PIX Master

📘 **Справка**

Очередь данных — встроенный в PIX Master брокер сообщений: она хранит транзакции и выдает их роботам по одной. Элементы кладут роботы, процессы мастера и внешние системы через API. Поля, статусы и настройки подробно описаны в [документации PIX Master](https://docs.pixrobotics.com/articles/#!rpa/master-queues). Ниже собрано то, что из этого нужно разработчику.

**Что можно положить в элемент:**

| Поле | Тип | Для чего |
|------|-----|----------|
| Значение | `string` | Основные данные транзакции, часто JSON |
| Входные данные | `Dictionary<string, object>` | Параметры транзакции по ключам |
| Выходные данные | `Dictionary<string, object>` | Результат обработки и метки прогресса ([QUEUE-11](#queue-11-отмечайте-в-элементе-очереди-выполненные-необратимые-шаги)) |
| Таблица | `DataTable` | Табличные данные: строки реестра, позиции заказа |
| Вложения | Файлы | Документы для обработки: сканы, письма, выгрузки |
| Ссылка | `string` | Ключ транзакции из источника, защита от дублей ([QUEUE-06](#queue-06-задавайте-элементу-очереди-уникальную-ссылку)) |
| Комментарий | `string` | Короткое пояснение для поддержки |

Порядок получения элемента и записи результата описан в [QUEUE-01](#queue-01-обрабатывайте-элемент-очереди-как-транзакцию), откладывание и повторы в [QUEUE-03](#queue-03-правильно-обрабатывайте-повторные-попытки-retry).

**Настройки очереди, от которых зависит код робота:**
- Повторы: «Использовать попытки», число попыток и задержка ([QUEUE-03](#queue-03-правильно-обрабатывайте-повторные-попытки-retry))
- Проверка уникальности ссылок ([QUEUE-06](#queue-06-задавайте-элементу-очереди-уникальную-ссылку))
- Максимальное время ожидания и максимальное время в статусе Processing ([QUEUE-07](#queue-07-ограничивайте-время-элемента-в-статусах-new-и-processing))
- SLA элемента: за сколько секунд с момента создания элемент должен быть обработан
