# Надежность и восстановление после сбоев

Робот работает без присмотра, поэтому любой сбой должен заканчиваться предсказуемо: транзакция либо обработана один раз, либо явно помечена ошибкой, а робот либо продолжает работу, либо останавливается с понятной причиной. Правила этого раздела дополняют [Соглашение об исключениях](error.md) и [Соглашение об очередях](../3-integrations/queue.md).

## RECOVERY-01. Делайте обработку транзакции идемпотентной

🔴 **Обязательно**

Идемпотентность означает, что повторная обработка той же транзакции не создает дубликатов и не меняет результат. Робот может упасть в любой момент: после создания документа в целевой системе, но до обновления статуса элемента очереди. При повторе он не должен создать второй документ.

**Как обеспечить:**
- Перед созданием объекта в целевой системе проверяйте, не создан ли он уже (поиск по номеру исходного документа, ID элемента очереди, хешу вложения)
- Сохраняйте во внешней системе ссылку на исходную транзакцию (номер элемента очереди в комментарии документа, в отдельном поле)
- Для операций, которые нельзя проверить (отправка письма, платеж), записывайте факт выполнения до перехода к следующему шагу и проверяйте эту запись при повторе
- Используйте в БД операции `MERGE` / `INSERT ... WHERE NOT EXISTS` вместо слепого `INSERT`

```csharp
// Шаг идемпотентен: при повторе транзакции документ не создается второй раз
var existingDocument = erpClient.FindDocumentBySourceId(queueItemId);
if (existingDocument == null)
    existingDocument = erpClient.CreateDocument(invoice, sourceId: queueItemId);
```

## RECOVERY-02. Сохраняйте прогресс многошаговых транзакций

🟡 **Рекомендуется**

Если транзакция состоит из нескольких длительных шагов (скачать документы → распознать → создать заявку → отправить уведомление), сохраняйте номер последнего успешно выполненного шага. При повторе робот продолжает с места сбоя, а не начинает сначала.

**Где хранить прогресс:**
- В данных элемента очереди, если PIX Master позволяет обновлять их в процессе обработки
- В служебной таблице БД робота с ключом по ID транзакции

Контрольные точки не отменяют [RECOVERY-01](#recovery-01-делайте-обработку-транзакции-идемпотентной): шаг мог выполниться, а сохранение контрольной точки — нет.

## RECOVERY-03. Восстанавливайте приложения после системного исключения

🟡 **Рекомендуется**

После системного исключения в UI-автоматизации приложение может остаться в неизвестном состоянии: открытый модальный диалог, незавершенная форма, разорванная сессия. Следующая транзакция в таком окружении тоже упадет.

**Порядок восстановления:**
1. Закройте приложения, с которыми работал робот (сначала штатно, затем принудительно через завершение процесса)
2. Заново выполните запуск и авторизацию — ту же логику, что в состоянии Init
3. Повторите транзакцию или переходите к следующей по правилам [QUEUE-04](../3-integrations/queue.md#queue-04-правильно-обрабатывайте-повторные-попытки-retry)

Вынесите закрытие и запуск приложений в отдельные скрипты, чтобы одна и та же логика использовалась и в Init, и при восстановлении.

## RECOVERY-04. Сохраняйте диагностику при системном исключении

🟡 **Рекомендуется**

Для разбора системной ошибки поддержке нужна не только запись в логе, но и состояние окружения в момент сбоя.

**Что сохранять:**
- Скриншот экрана (для UI-автоматизации)
- Название активного окна и состояния робота, в котором произошла ошибка
- Идентификатор транзакции и номер попытки

**Ограничения:**
- Если на экране могут быть персональные данные, скриншоты хранятся с ограниченным доступом и удаляются по сроку (см. [PRIVACY-03](privacy.md#privacy-03-ограничивайте-доступ-к-скриншотам-и-артефактам-с-персональными-данными))
- Не сохраняйте скриншоты при бизнес-исключениях: они штатные и не требуют разбора

## RECOVERY-05. Останавливайте робота после серии системных исключений подряд

🔴 **Обязательно**

Если несколько транзакций подряд падают с системным исключением, проблема почти наверняка в окружении, а не в данных: недоступна целевая система, истек пароль, изменился интерфейс. Продолжая работу, робот переведет в ошибку всю очередь.

**Правила:**
- Считайте системные исключения подряд; успешная транзакция или бизнес-исключение сбрасывают счетчик
- Порог (обычно 3–5) храните в ассете, а не в коде
- При достижении порога робот завершает работу через End Process со статусом ошибки и понятным сообщением: «Остановлен после 3 системных ошибок подряд. Последняя: …»
- Остановка по порогу должна вызывать оповещение поддержки (см. [мониторинг в PIX Master](https://github.com/TheMrDJek/pix-rpa-process/blob/main/docs/admin/monitoring.md))

## RECOVERY-06. Проверяйте сигнал остановки от мастера

🔴 **Обязательно**

Администратор должен иметь возможность штатно остановить робота: перед обновлением, при инциденте, при окончании окна работы. Робот проверяет сигнал остановки перед взятием каждой новой транзакции (в состоянии Get Transaction) и при его получении переходит в End Process.

Не проверяйте сигнал остановки в середине транзакции: транзакция должна завершиться целиком, чтобы не оставить данные в промежуточном состоянии.
