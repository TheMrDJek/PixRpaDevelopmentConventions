# Имена параметров и переменных

По имени переменной должно быть понятно, какие данные она хранит. Имена `path1` и `path2` не объясняют, где исходный файл, а где его архивная копия. Чтобы выбрать нужную переменную в активности, разработчику приходится искать, откуда взялось каждое значение. Имена `sourceFilePath` и `archiveFilePath` сразу показывают это различие.

По понятному имени разработчик быстрее определит, какое значение проверить при ошибке, без поиска всех мест, где переменной что-то присваивают. Уточняйте имя, если без этого можно перепутать значения.

Общие требования к стилю описаны в [CODE-01](code.md#code-01-соблюдайте-принятые-соглашения-о-коде), имена проектов, папок и скриптов в разделе [Именование проекта](../1-project/naming.md).

## VARIABLE-01. Обозначайте направление параметра в имени

🔴 **Обязательно**

Начинайте имя параметра скрипта PIX с `in_`, `out_` или `io_`. Префикс должен совпадать с направлением, которое вы задали у параметра. Остальную часть имени пишите в PascalCase, без подчёркиваний между словами. Например, `in_OrderNumber`.

По префиксу при чтении выражения видно, какие данные скрипт получает и какие возвращает. Сам префикс направление передачи не задаёт.

В активности «Выполнить скрипт» укажите, откуда взять входные данные и куда записать результат. В примере в колонке «Значение» стоят переменные вызывающего скрипта.

| Параметр | Значение | Что происходит при вызове |
|---|---|---|
| `in_OrderNumber` | `orderNumber` | Скрипт получает номер заказа. |
| `out_OrderStatus` | `orderStatus` | Скрипт возвращает статус заказа в `orderStatus`. |
| `io_RetryCount` | `retryCount` | Скрипт получает текущее число повторов и возвращает обновлённое в ту же переменную. |

Для параметров методов C# используйте camelCase без префиксов направления, например `orderNumber`.

## VARIABLE-02. Используйте camelCase для локальных переменных

🔴 **Обязательно**

Начинайте имя локальной переменной со строчной буквы, каждое следующее слово с заглавной: `orderNumber`, `customerEmail`, `retryCount`. Применяйте этот формат в таблице переменных скрипта и в C#-коде.

Префиксы `in_`, `out_`, `io_` оставляйте для параметров скрипта. Для констант `const` используйте [PascalCase](#константы-и-магические-значения).

## VARIABLE-03. Называйте переменные по смыслу данных

🔴 **Обязательно**

Указывайте в имени, что хранит переменная. Добавьте роль, состояние или единицу измерения, если без них можно перепутать значения. Для списка заказов подходит `orders`. Если в скрипте есть ещё список уже обработанных заказов, назовите списки `ordersToProcess` и `processedOrders`.

| Неудачное имя | Имя по смыслу | Что проясняет имя |
|---|---|---|
| `data` | `ordersToProcess` | Заказы, которые предстоит обработать. |
| `result` | `createdInvoiceNumber` | Номер созданного счёта. |
| `date` | `invoiceDueDate` | Срок оплаты счёта. |
| `path` | `invoiceTemplatePath` | Путь к шаблону счёта. |
| `timeout` | `timeoutSeconds` | Время ожидания в секундах. |
| `strSubject` | `emailSubject` | Тема письма. Тип строки указан отдельно. |
| `boolIsActive` | `isActive` | Текущее состояние. Тип `bool` уже задан. |
| `in_StrFilePath` | `in_SourceFilePath` | Входной параметр с путём к исходному файлу. |
| `customerEmailStringValue` | `customerEmail` | Адрес заказчика. Слова `StringValue` ничего не уточняют. |

Не дублируйте тип в имени. Тип смотрите в таблице переменных Studio или в редакторе C#. Префиксы `in_`, `out_`, `io_` сохраняйте для [направления передачи параметров](#variable-01-обозначайте-направление-параметра-в-имени). В коротком цикле достаточно индекса `i`, если его роль понятна из кода.

### Константы и магические значения

Число или строку называют магическими, когда по выражению нельзя понять их смысл. Дайте такому значению имя или возьмите его из настроек, если его нужно менять без правки кода.

| Неудачный пример | Что написать | Почему |
|---|---|---|
| `orderNumber?.Length == 8` | `orderNumber?.Length == OrderNumberLength` | Имя показывает, что длину задаёт формат номера в выгрузке. |
| `statusCode == "CNL"` | `statusCode == CancelledStatusCode` | По имени видно, что код означает отмену заказа. |
| `row[3]` | `row["OrderNumber"]` | Заголовок показывает, откуда берётся номер заказа. Если заголовков нет, назовите индекс `OrderNumberColumnIndex`. |
| `retryCount >= 3` | `retryCount >= maxRetryCount` | Если лимит меняет поддержка, загрузите `maxRetryCount` из настроек. |

В C#-блоке активности «Выполнить» объявляйте неизменяемые значения через `const`, если они известны при компиляции. Имена констант пишите в PascalCase. [Соглашения об именовании в C#](https://learn.microsoft.com/ru-ru/dotnet/csharp/fundamentals/coding-style/identifier-names#naming-conventions).

```csharp
const int OrderNumberLength = 8;
const string CancelledStatusCode = "CNL";

bool hasExpectedLength = orderNumber?.Length == OrderNumberLength;
bool isCancelled = statusCode == CancelledStatusCode;
```

Используйте литерал, когда его смысл виден из выражения. Например, `rows.Count == 0` проверяет, что строк нет.

Если одно фиксированное значение нужно нескольким активностям, задайте его в таблице переменных скрипта и обращайтесь к нему по имени в camelCase, например `orderNumberLength`. Такую переменную по-прежнему можно изменить присваиванием. Таймауты, получателей писем и другие значения, которые меняют без правки логики, храните в настройках по [CONFIG-01](../1-project/config.md#config-01-не-зашивайте-настройки-в-код).

## VARIABLE-04. Не используйте кириллицу в именах

🔴 **Обязательно**

Кириллица в именах переменных и параметров запрещена, в том числе в сочетании с латинскими буквами. Пишите имена английскими словами. Транслитерацию вроде `imyaZakazchika` тоже не используйте.

| Не используйте | Используйте |
|---|---|
| `имяЗаказчика` | `customerName` |
| `in_НомерЗаказа` | `in_OrderNumber` |
| `customerИмя` | `customerName` |

Для имён скриптов действует тот же запрет по [NAMING-04](../1-project/naming.md#naming-04-используйте-в-именах-только-латиницу-и-цифры). Например, называйте скрипт `SendInvoice` вместо `ОтправитьСчёт`.

Единый язык имён помогает находить связанные данные по одному термину, например `customer`. Это соглашение команды. C# технически допускает кириллицу в идентификаторах.

Подписи активностей, комментарии и текстовые значения могут содержать русский текст, например тему письма «Счёт обработан».

## VARIABLE-05. Используйте одинаковые термины для одинаковых понятий

🟡 **Рекомендуется**

Выберите термин для каждого понятия процесса и используйте его во всём проекте. Если заказчика называете `customer`, называйте связанные данные `customerId`, `customerEmail`, `customerOrders`. Чередование `customer` и `client` для одного заказчика заставляет искать различие, которого нет.

Сохраняйте различия между понятиями. Если процесс различает закупочную цену и цену продажи, используйте `purchasePrice` и `salePrice`. Количество товара и его объём называйте `quantity` и `volume`. Выбор общего слова для таких значений скроет смысл расчёта.

При выборе имени можно свериться с [таблицей терминов предметной области](../1-project/naming.md#объекты-по-бизнес-направлениям). Используйте выбранное слово и в имени скрипта, и в его параметрах и переменных. Например, `GetSupplier` принимает `in_SupplierId`, которому передают `supplierId`. В скрипте `CreateInvoice` номер счёта хранится в `invoiceNumber` и возвращается через `out_InvoiceNumber`.

## VARIABLE-06. Называйте логические переменные так, чтобы было понятно значение true

🟡 **Рекомендуется**

Называйте переменную типа `bool` по состоянию или результату проверки. Читатель должен понимать, что означает `true`, без поиска места, где переменной присвоили значение.

| Имя | Что означает `true` |
|---|---|
| `hasAttachments` | У письма есть вложения. |
| `isEmailValid` | Адрес почты прошёл проверку. |
| `canRetry` | Разрешена ещё одна попытка. |

Начала `is`, `has`, `can` часто помогают сформулировать имя, но не обязательны. Избегайте имён вроде `flag` и `checkAttachments`: по ним непонятно, что означает результат.

Выбирайте имена, с которыми легко читать условия. `hasAttachments` читается как «у письма есть вложения», а `!hasAttachments` как «вложений нет». В выражении `!hasNoAttachments` приходится разбирать двойное отрицание.

При замене `hasNoAttachments` на `hasAttachments` измените присваивания и условия: для одного и того же письма значения этих переменных противоположны. Одного переименования недостаточно.

Сохраняйте смысл состояний процесса. `isNotRejected` нельзя автоматически заменить на `isApproved`: заявка может ожидать решения. Имена `hasErrors` и `isEmpty` допустимы, поскольку прямо описывают состояние.
