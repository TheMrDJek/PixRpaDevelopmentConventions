# Именование проекта

Как называть проект робота, папки и скрипты. С едиными именами в любом проекте нужный скрипт находится сразу, а по имени проекта понять, какой это робот в PIX Master и какой репозиторий в Git. Имена параметров и переменных описаны в разделе [Имена параметров и переменных](../2-develop/variable.md).

> [!NOTE]
> 🚧 **Новый раздел.** Правила сформулированы по существующим соглашениям о структуре проекта и именах в PIX Master; сверьте их с практикой команды.

## NAMING-01. Называйте проект так же, как робота в PIX Master

🔴 **Обязательно**

Проект робота, репозиторий Git и робот в PIX Master называются одинаково, по формату `{Проект}_{Процесс}` (см. [MASTER-01](../4-master/master.md#master-01-именуйте-агентов-по-типу-робота)):

| Что | Имя |
|-----|-----|
| Проект PIX RPA | `AP_InvoiceProcessing` |
| Репозиторий Git | `AP_InvoiceProcessing` |
| Робот в PIX Master | `AP_InvoiceProcessing_Bot01` |

Для схемы Dispatcher/Performer (см. [справку](project.md#dispatcher--performer-когда-делить-процесс-на-несколько-роботов)) это два проекта: `AP_InvoiceDispatcher` и `AP_InvoicePerformer`.

**Почему:** по сообщению об ошибке из мастера поддержка сразу находит проект и репозиторий, не спрашивая автора.

## NAMING-02. Используйте стандартные имена папок

🔴 **Обязательно**

Папки называются так же, как в структуре проекта из [TEMPLATE-01](template.md#template-01-разделяйте-проект-на-слои), без синонимов: `Common`, `Helpers`, `Infrastructure`, `States`, `Tests` и папки состояний внутри `States`.

- Не заводите параллельные папки с похожим смыслом: `Utils`, `Tools`, `Misc`, `Scripts`, `New folder`
- Папки внутри `Infrastructure` называются по внешней системе или каналу: `1C`, `Crm`, `Wms`, `Mail`, `DataBase`, `PixMaster`
- Папки транзакций внутри состояния называются по типу транзакции: `States/Process/Transactions/AddOrderItem`. Шаги, общие для нескольких типов, лежат в `Transactions/Shared` (см. [«Сценарий транзакции»](template.md#сценарий-транзакции-паттерн-transaction-script))
- Папка для End Process не обязательна: если завершение помещается в блок `main.pix`, ее нет

**Почему:** в любом проекте команды скрипт ищется по одному и тому же пути.

## NAMING-03. Называйте скрипт глаголом и объектом

🔴 **Обязательно**

Имя скрипта отвечает на вопрос «что он делает»: глагол + объект в PascalCase.

| Хорошо | Плохо |
|--------|-------|
| `GetCustomer` | `Customer`, `Script1` |
| `CreateInvoice` | `Invoice_new`, `Обработка` |
| `SendDailyReport` | `Report2`, `SendReportFinal` |
| `IsInvoiceValid` | `CheckInvoice` (непонятно, что вернет) |

- Скрипт, который возвращает логическое значение, называйте как вопрос: `Is…`, `Has…`, `Can…` (см. [VARIABLE-10](../2-develop/variable.md#variable-10-избегайте-абстрактных-названий))
- Не повторяйте в имени скрипта название папки: `Infrastructure/Mail/Send`, а не `Infrastructure/Mail/MailSend`
- Не используйте в именах версии и статусы: `_old`, `_new`, `_v2`, `_final`. История версий хранится в Git
- Тестовые скрипты называйте по правилу [TEST-05](../2-develop/test.md#test-05-именуйте-и-структурируйте-тесты-единообразно)

**Почему:** по имени скрипта на схеме процесса понятно, что происходит, без открытия скрипта.

## NAMING-04. Используйте латиницу без пробелов в именах проектов, папок и файлов

🔴 **Обязательно**

В именах проектов, папок, скриптов, ресурсов и других файлов проекта используйте только латиницу, цифры и `_`, без пробелов: `ReportTemplate.xlsx`, а не `Шаблон отчета.xlsx`.

**Почему:**
- Пробелы и кириллица в путях ломают командную строку, часть библиотек и сравнение путей в Git на разных машинах
- Кириллица в именах файлов по-разному кодируется в архивах и на сетевых дисках
- Одинаковое правило для имен файлов и имен в коде (см. [VARIABLE-06](../2-develop/variable.md#variable-06-не-используйте-кириллицу-в-именах)) проще запомнить
