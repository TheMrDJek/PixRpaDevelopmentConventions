# Именование проекта

Как называть проект робота, папки и скрипты. Единые имена нужны, чтобы сопровождать робота, в одиночку или в команде. Через полгода автор открывает свой проект как чужой, а в команде робота открывают ревьюер, поддержка и новый разработчик. По имени задачи в PIX Master каждый из них находит проект и его папку в Git, а в проекте нужный скрипт, не вспоминая и не спрашивая автора ([«Зачем это нужно»](../../README.md#зачем-это-нужно)). Имена параметров и переменных описаны в разделе [Имена параметров и переменных](../2-develop/variable.md), имена ассетов в [CONFIG-06](config.md#config-06-именуйте-ассеты-по-типу).

## NAMING-01. Называйте проект по домену и решению

🔴 **Обязательно**

Проект робота в PIX Studio и проект в PIX Master называются одинаково. Имя складывается из частей через точку, внутри части слова пишутся в PascalCase, без `_` и `-`:

| Часть | Что это | Пример |
|-------|---------|--------|
| Домен | Бизнес-направление, к которому относится робот. Всегда одна часть | `Orders`, `Finance`, `HR` |
| Решение | Один робот или связка роботов, которые вместе автоматизируют одну работу | `Orders.ProcessOrderRequest`, `Finance.CloseMonth` |
| Роль | Робот внутри связки. Есть, только если решение состоит из нескольких роботов | `Finance.ProcessInvoices.Dispatcher`, `Finance.ProcessInvoices.Performer` |

Решение устроено как solution в C#: в Visual Studio solution объединяет несколько проектов, а здесь решение объединяет проекты роботов. Решение из одного робота называется в две части: `{Домен}.{Решение}`. Связка роботов, например [Dispatcher и Performer](project.md#когда-делить-решение-на-роботов-dispatcher--performer-и-цепочки), получает третью часть: `{Домен}.{Решение}.{Роль}`. Роботы одного решения стоят в списке рядом.

Роль называйте по работе робота в решении. Dispatcher и Performer это только одна из схем, и делить решение на поставщика и обработчика не обязательно. Сколько роботов в решении, решают при проектировании ([плюсы и минусы разделения](project.md#плюсы-и-минусы-разделения)), а имя только отражает это деление:

| Решение | Проекты | Как устроено |
|---------|---------|--------------|
| Один робот | `Orders.ProcessOrderRequest` | Робот сам берет заявку, обрабатывает ее в 1С и отвечает. Роли нет |
| Поставщик и обработчик | `Finance.ProcessInvoices.Dispatcher`, `Finance.ProcessInvoices.Performer` | Dispatcher читает реестр счетов и кладет счета в очередь, Performer проводит каждый счет |
| Конвейер из трех роботов | `Sales.IncomingDocuments.FetchMail`, `Sales.IncomingDocuments.Recognize`, `Sales.IncomingDocuments.LoadToCrm` | Первый робот забирает письма и кладет вложения в очередь `Sales.IncomingDocuments.ToRecognize`. Второй распознает документы и кладет результат в очередь `Sales.IncomingDocuments.ToCrm`. Третий загружает данные в CRM |

| Что | Имя |
|-----|-----|
| Папка проекта и файл проекта | `Orders.ProcessOrderRequest`, `Orders.ProcessOrderRequest.pixproj` |
| Проект в PIX Master | `Orders.ProcessOrderRequest` |
| Задача в PIX Master | Начинается с имени проекта ([MASTER-03](../4-master/master.md#master-03-именуйте-задачи-по-формату-проект_процесс_периодичность)) |
| Процесс мастера | Если он связывает роботов решения, называется по решению: `Finance.ProcessInvoices` |

**Что дает одно имя из частей.** Имя проекта видят в PIX Master, в PIX Studio и в Git, и везде оно ведет к одному роботу:
- По имени проекта или задачи в PIX Master поддержка находит папку проекта в Git и открывает ее в PIX Studio, не спрашивая автора
- Точка разделяет уровни имени: домен, решение, роль. В списках PIX Master сортировка по имени собирает роботов одного домена и одного решения вместе
- У ассета последняя часть имени это настройка, а `_` отделяет контур, поэтому имя разбирается однозначно

Имя проекта в коде берите из входного параметра или `config`, а не из имени папки проекта. `Path.GetExtension` и `Path.GetFileNameWithoutExtension` примут часть после последней точки за расширение файла.

«Решение» не путайте с процессом мастера: процесс мастера это схема из блоков в PIX Master, которая запускает задачи и работает с очередями. У решения из одного робота, которого запускает расписание, процесса мастера обычно нет.

**Репозиторий Git** может хранить несколько проектов: всех роботов домена или одного решения. Как делить роботов по репозиториям, решает команда. Папка проекта в репозитории называется как проект, поэтому робота из PIX Master находят в любом репозитории по имени папки:

```console
Finance                                  репозиторий домена
├───Finance.CloseMonth
│   └───Finance.CloseMonth.pixproj
├───Finance.ProcessInvoices.Dispatcher
│   └───Finance.ProcessInvoices.Dispatcher.pixproj
└───Finance.ProcessInvoices.Performer
    └───Finance.ProcessInvoices.Performer.pixproj
```

### Домен

Домен это [бизнес-направление](../glossary.md), к которому относится робот. Обычно это направление заказчика робота. Один домен объединяет несколько решений:

| Домен | Направление | Проекты |
|-------|-------------|---------|
| `Orders` | Заказы клиентов | `Orders.ProcessOrderRequest`, `Orders.SendDailyReport` |
| `Suppliers` | Работа с поставщиками | `Suppliers.FetchAct`, `Suppliers.ReconcileInvoices` |
| `Finance` | Бухгалтерия и финансы | `Finance.CloseMonth`, `Finance.ProcessInvoices.Dispatcher` |
| `Sales` | Продажи и работа с клиентами | `Sales.IncomingDocuments.Recognize`, `Sales.UpdateCustomerCards` |
| `HR` | Кадры | `HR.OnboardEmployee`, `HR.ProcessVacationRequest` |
| `Prices` | Мониторинг цен | `Prices.ParseSites` |

- Домен всегда из одной части. В имени `Finance.Payables.ProcessInvoices` не понять, где домен, а где решение. Большое направление сделайте отдельным доменом: `Payables`
- Домен уже задает контекст, поэтому решение называйте коротко: `Finance.CloseMonth`, а не `Finance.CloseFinanceMonth`
- Список доменов ведите один на команду: новый домен заводите под новое направление, а не под каждого робота

**Зачем домен, когда роботов много.** Пока роботов десять, их помнят по именам. Когда их сотня, в PIX Master сотни задач, ассетов и очередей, и без домена это один длинный список:
- Сортировка по имени собирает задачи, ассеты и очереди одного направления вместе. Разработчик видит все, что относится к заказам, а не ищет по памяти
- По домену понятно, чей это робот и к кому идти с вопросом: заказы к отделу продаж, `Finance` к бухгалтерии
- Одинаковые имена решений не конфликтуют: `Orders.SendDailyReport` и `Finance.SendDailyReport` это два разных робота
- Настройку, общую для роботов направления, заводят один раз: `Orders.ProcessOwnerEmails` читают все роботы домена `Orders`
- Один Dispatcher может обслуживать весь домен в [доменном формате](project.md#доменный-формат)

Домен ставьте и тогда, когда роботов пока мало. Переименовать потом придется проект, его папку в Git, задачи, ассеты и очереди на всех контурах.

### Ассеты и очереди

Ассет и очередь называются по самому узкому уровню, на котором их используют:

| Уровень | Когда | Пример |
|---------|-------|--------|
| Общий | Нужен роботам разных доменов: почтовый сервер, адреса поддержки RPA. Первая часть имени это система или `Rpa` | `Smtp.Server`, `Rpa.SupportEmails` |
| Домен | Одинаков для всех решений направления | `Orders.ProcessOwnerEmails` |
| Решение | Нужен роботам решения: БД, очередь, получатели отчета, правила, фильтры | `Orders.ProcessOrderRequest.ReportRecipients` |
| Роль | Нужен одному роботу из связки | `Finance.ProcessInvoices.Dispatcher.MailFilter` |

У решения из одного робота уровни решения и робота совпадают, поэтому его настройки лежат на уровне решения. Уровень роли нужен редко. Когда ассет понадобится второму решению, поднимите его на уровень выше и переименуйте.

Если значение зависит от контура, добавьте к имени суффикс контура через `_`: `Orders.ProcessOrderRequest.ReportRecipients_Prod` ([CONFIG-06](config.md#config-06-именуйте-ассеты-по-типу)).

Длинное имя ассета встречается только в PIX Master и в одном месте кода. Init сопоставляет его с [коротким ключом `config`](config.md), и дальше скрипты пишут `config["ReportRecipients"]`.

## NAMING-02. Используйте стандартные имена папок

🔴 **Обязательно**

Папки называются так же, как в структуре проекта из [TEMPLATE-01](template.md#template-01-раскладывайте-скрипты-по-папкам-по-роли), без синонимов и номеров:

- Верхний уровень: `Common`, `Helpers`, `Infrastructure`, `States`, `Tests`
- Папки состояний внутри `States`: `Init`, `GetTransaction`, `Process`, `EndProcess`. Скрипты состояния лежат в его папке. Папка `EndProcess` не обязательна: если завершение помещается в блок `main.pix`, ее нет
- Внутри `Process`: `Transactions` для [сценариев](template.md#сценарий-транзакции-паттерн-transaction-script) по типам транзакций и `Strategies` для [стратегий](template.md#варианты-процесса-стратегия). Папка сценария называется по типу транзакции: `Transactions/AddOrderItem`, шаги, общие для нескольких типов, лежат в `Transactions/Shared`. Папка стратегии называется по варианту: `Strategies/AgroSite01`
- Внутри `Infrastructure`: по папке на внешнюю систему или канал: `1C`, `Crm`, `Wms`, `Mail`, `DataBase`, `PixMaster`, `FileSystem`
- Внутри `Tests`: `UnitTests` и `IntegrationTests` ([TEST-05](../2-develop/test.md#test-05-именуйте-и-структурируйте-тесты-единообразно))

Не заводите параллельные папки с похожим смыслом: `Utils`, `Tools`, `Misc`, `Scripts`, `New folder`. Не нумеруйте папки состояний: `Init`, а не `1 Init`. Порядок состояний задает `main.pix`, а номера при новом состоянии пришлось бы переписывать в папках и путях вызова.

**Зачем одинаковые папки во всех проектах.** В чужом проекте разработчик и поддержка ищут скрипт по тому же пути, что и в своем: запуск приложений в `States/Init`, работу с 1С в `Infrastructure/1C`.

## NAMING-03. Называйте скрипт по тому, что он делает

🔴 **Обязательно**

Имя скрипта отвечает на вопрос «что он делает»: глагол + объект в PascalCase, как имя метода в C#.

| Хорошо | Плохо |
|--------|-------|
| `GetCustomer` | `Customer`, `Script1` |
| `CreateInvoice` | `Invoice_new`, `Обработка` |
| `SendDailyReport` | `Report2`, `SendReportFinal` |
| `IsInvoiceValid` | `CheckInvoice` (непонятно, что вернет) |

- Стартовый скрипт проекта называется `main.pix` и лежит в корне проекта. Это исключение из правила «глагол + объект»: стартовый скрипт указывают при загрузке проекта в PIX Master, и с одним именем во всех проектах его не приходится искать
- Скрипт, который возвращает логическое значение, называйте как вопрос: `Is…`, `Has…`, `Can…` ([VARIABLE-10](../2-develop/variable.md#variable-10-избегайте-абстрактных-названий)). Скрипт, который проверяет и при ошибке бросает исключение, начинайте с `Validate`: `ValidateEnvironment`
- Имя понятно без пути: `Start1C`, `SendMail`, а не `Start`, `Send`. Повторить в имени название папки можно: `Infrastructure/1C/Start1C`. Скрипт с коротким именем в поиске по проекту не отличить от соседей
- Если скрипт вызывают по пути, собранному из имени папки, во всех таких папках он называется одинаково: `Strategies/AgroSite01/ExtractPrices`, `Strategies/AgroSite02/ExtractPrices`
- Один глагол во всем проекте значит одно и то же. `Get` возвращает данные и ничего не меняет, `Find` может ничего не найти. Выбрали `Get`, не называйте то же действие `Load`, `Fetch` или `Read`. Частые глаголы и их смысл собраны в справке [«Частые слова в именах скриптов»](#частые-слова-в-именах-скриптов)
- Избегайте слов, которые не говорят, что делает скрипт: `Handle`, `Manage`, `Do`, `Work`, а в роли объекта `Data`, `Info`, `Helper`, `Utils` ([VARIABLE-10](../2-develop/variable.md#variable-10-избегайте-абстрактных-названий)). `Process` и `Run` годятся только с конкретным объектом, когда скрипт запускает сценарий: `RunRequestScenario`, а не `ProcessData`
- Не используйте в именах версии и статусы: `_old`, `_new`, `_v2`, `_final`. История версий хранится в Git
- Тестовые скрипты называйте по правилу [TEST-05](../2-develop/test.md#test-05-именуйте-и-структурируйте-тесты-единообразно)

**Зачем называть скрипт по действию.** Скрипт находят по имени в поиске по проекту и видят его в пути активности «Выполнить скрипт». Имя-действие говорит, что сделает вызов, и скрипт не приходится открывать. Цепочка вызовов в состоянии читается как список действий: `GetQueueItem`, `FindContractor`, `PostDocument`. По имени `DoWork` или `ProcessData` остается гадать, что внутри, и скрипт открывают каждый раз.

## NAMING-04. Используйте в именах только латиницу и цифры

🔴 **Обязательно**

В именах проектов, папок, скриптов, ресурсов и других файлов проекта используйте только латиницу и цифры, без пробелов, `-` и `_`. Слова разделяйте PascalCase: `ReportTemplate.xlsx`, а не `Шаблон отчета.xlsx` или `report_template.xlsx`.

Исключения:
- Точка разделяет домены в имени проекта и задачи ([NAMING-01](#naming-01-называйте-проект-по-домену-и-решению))
- `_` отделяет контур в имени ассета и очереди ([CONFIG-06](config.md#config-06-именуйте-ассеты-по-типу))
- `_` разделяет части имени теста ([TEST-05](../2-develop/test.md#test-05-именуйте-и-структурируйте-тесты-единообразно))

**Чем мешают пробелы, кириллица и разделители:**
- Путь с пробелами в командной строке и в коде нужно брать в кавычки, и забытые кавычки ломают путь
- Кириллица в именах файлов по-разному кодируется в ZIP-архивах и на сетевых дисках
- Когда слова разделяет только PascalCase, имя записывают одним способом и находят поиском с первого раза
- То же правило действует для имен в коде ([VARIABLE-06](../2-develop/variable.md#variable-06-не-используйте-кириллицу-в-именах))

## Частые слова в именах скриптов

📘 **Справка**

Дополняет [NAMING-03](#naming-03-называйте-скрипт-по-тому-что-он-делает). Таблицы помогают назвать скрипт так же, как его назвали бы в соседнем роботе. Глаголы сгруппированы по виду работы, а объекты по бизнес-направлениям.

### Глаголы

**Данные в любой системе: 1С, CRM, API, БД.** Для API и БД берите те же глаголы, что и для записей в 1С: `GetOrder` читает заказ и через интерфейс, и через REST.

| Глагол | Что делает скрипт | Пример |
|--------|-------------------|--------|
| `Get` | Возвращает данные и ничего не меняет | `GetQueueItem`, `GetStockBalance` |
| `Find` | Ищет запись. Может не найти и вернуть пусто | `FindContractor` |
| `Create` | Создает новую запись | `CreateInvoice` |
| `Add` | Добавляет в существующий документ, список или очередь | `AddOrderLine`, `AddResponseItem` |
| `Update` | Меняет существующую запись | `UpdateOrderStatus` |
| `Delete` | Удаляет запись | `DeleteDraftOrder` |
| `Post`, `Approve`, `Sign` | Проводит, согласует или подписывает документ | `PostDocument`, `ApproveInvoice` |
| `Export`, `Import` | Выгружает из системы или загружает в нее | `ExportOrderReport`, `ImportPrices` |

**Интерфейс приложения.**

| Глагол | Что делает скрипт | Пример |
|--------|-------------------|--------|
| `Start`, `Kill` | Запускает приложение или завершает его процесс | `Start1C`, `KillProcess` |
| `Login` | Входит в систему | `LoginToPortal` |
| `Open`, `Close` | Открывает или закрывает окно, форму, карточку | `OpenOrderCard`, `CloseAllWindows` |
| `Fill` | Заполняет форму | `FillPaymentForm` |
| `Select` | Выбирает значение в списке или строку в таблице | `SelectContractor` |
| `WaitFor` | Ждет появления окна, элемента или файла | `WaitForReport` |

**Файлы и почта.**

| Глагол | Что делает скрипт | Пример |
|--------|-------------------|--------|
| `Read`, `Write` | Читает или пишет файл | `ReadRegistry`, `WriteReport` |
| `Copy`, `Move` | Копирует или переносит файл, письмо | `CopyToArchive`, `MoveMailToProcessed` |
| `Download`, `Upload` | Скачивает с сайта, портала, хранилища или загружает туда | `DownloadBankStatement`, `UploadProtocol` |
| `Send`, `Reply` | Отправляет письмо или сообщение, отвечает на письмо | `SendDailyReport`, `ReplyToSender` |
| `Save` | Сохраняет вложения или данные в файл | `SaveAttachments` |

**Разбор, расчет и проверка.**

| Глагол | Что делает скрипт | Пример |
|--------|-------------------|--------|
| `Parse`, `Extract` | Разбирает строку или документ, достает из него данные | `ParseOrderNumber`, `ExtractPrices` |
| `Convert` | Переводит данные из одного формата в другой | `ConvertXlsToXlsx` |
| `Build` | Собирает отчет, письмо, протокол из готовых данных | `BuildDisagreementProtocol` |
| `Calculate` | Считает значение | `CalculateVat` |
| `Compare` | Сравнивает два набора данных | `CompareActWithLedger` |
| `Validate` | Проверяет и при ошибке бросает исключение | `ValidateEnvironment` |
| `Is`, `Has`, `Can` | Возвращает логическое значение | `IsInvoiceValid`, `HasAttachments` |

### Объекты по бизнес-направлениям

У одного бизнес-термина часто несколько верных переводов: контрагент это и `Contractor`, и `Counterparty`. Выберите один вариант и используйте его во всем проекте, а в роботах одного домена лучше тот же. Если в одном проекте встречаются `FindContractor` и `GetCounterparty`, читатель решит, что это разные сущности. В колонке «Принято чаще» вариант, который чаще встречается в роботах и интеграциях с 1С в России и СНГ. Российские сокращения не переводите, а пишите латиницей в PascalCase: `Inn`, `Kpp`, `Upd`.

| Термин | Принято чаще | Другие варианты | Пример |
|--------|--------------|-----------------|--------|
| Контрагент | `Contractor` | `Counterparty`, `Partner` | `FindContractor` |
| Поставщик | `Supplier` | `Vendor` | `GetSupplier` |
| Покупатель | `Customer` | `Buyer`, `Client` | `GetCustomer` |
| Договор | `Contract` | `Agreement` | `GetContract` |
| Счет на оплату | `Invoice` | `Bill` | `CreateInvoice` |
| УПД | `Upd` | | `PostUpd` |
| Накладная | `Waybill` | `DeliveryNote` | `CreateWaybill` |
| Заказ | `Order` | | `GetOrder` |
| Заявка, запрос | `Request` | `Application` | `CreateRequest` |
| Платеж, платежное поручение | `PaymentOrder` | `Payment` | `CreatePaymentOrder` |
| Банковская выписка | `BankStatement` | `Statement` | `DownloadBankStatement` |
| Акт сверки | `ReconciliationAct` | `ReconciliationStatement` | `ExtractReconciliationAct` |
| Протокол разногласий | `DisagreementProtocol` | `DiscrepancyReport` | `BuildDisagreementProtocol` |
| Сальдо | `Balance` | | `GetBalance` |
| Проводка | `Entry` | `Posting` | `GetEntries` |
| Номенклатура | `Product` | `Item` | `FindProduct` |
| Склад | `Warehouse` | | `GetWarehouse` |
| Остаток | `Stock` | `Balance` | `GetStockBalance` |
| Сотрудник | `Employee` | | `GetEmployee` |
| Отпуск | `Vacation` | `Leave` | `CreateVacationRequest` |
| ИНН, КПП, БИК | `Inn`, `Kpp`, `Bik` | | `FindContractorByInn` |

Слова с несколькими значениями уточняйте объектом:
- `Contractor` в английском значит еще и «подрядчик». Если робот работает и с контрагентами, и с подрядчиками, подрядчика назовите `Subcontractor`
- «Счет» бывает счетом на оплату (`Invoice`), банковским счетом (`BankAccount`) и счетом учета (`LedgerAccount`)
- «Акт» без уточнения не пишите: акт сверки это `ReconciliationAct`, акт выполненных работ `CompletionAct`
- `PaymentOrder` это документ, платежное поручение. Если робот работает с фактом оплаты из выписки, а не с документом, берите `Payment`
