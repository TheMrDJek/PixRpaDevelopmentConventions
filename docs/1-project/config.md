# Конфигурация и конфиденциальные данные

Где робот берет настройки и секреты, как называть ассеты в PIX Master и как собрать их в словарь `config`.

> [!NOTE]
> Раздел описывает робота, который работает с PIX Master. Без мастера настройки и секреты хранят в другом месте: в БД, файле, Excel, Vault или другом хранилище секретов. Где их хранить, решают отдельно для каждого робота.

## Что такое ассет

📘 **Справка**

Ассет это параметр робота, который хранится в PIX Master. В интерфейсе мастера ассеты лежат в разделе [«Данные» (Data)](https://docs.pixrobotics.com/articles/#!rpa/master-data).

**Ассет в мастере.** У ассета есть ключ, описание, тип, значение и группа. Типов пять: строка, число, логическое значение, защищенные данные и учетные данные.

Значение задают глобально или отдельно для агента. Если для агента значения нет, робот получит глобальное. Отдельные значения нужны, например, для учетных записей: каждый агент входит в систему под своей.

**Ассет в роботе.** Робот читает ассеты в состоянии Init и собирает их в словарь `config` ([«Как собрать `config` из ассетов»](#как-собрать-config-из-ассетов)). Дальше скрипты берут значения из `config`.

| Что нужно получить | Активность PIX | Что вернет |
|--------------------|----------------|------------|
| Строку, число или логическое значение | Получение типизированных данных по ключу | String, Int32 или Boolean |
| Любой ассет, кроме учетных данных | Получение данных | String |
| Защищенные данные | Получение данных как SecureString | SecureString |
| Учетные данные | Получение учетных данных | Логин: String или SecureString. Пароль: SecureString |

Активность «Получение данных» возвращает строку для всех типов. Число и логическое значение придется преобразовать самим, поэтому для них удобнее типизированная активность.

Робот может и записывать ассеты: есть активности обновления данных и учетных данных. Запись меняет глобальное значение для всех роботов, которые читают этот ассет. Используйте ее, только если это часть процесса, например робот сам меняет пароль по расписанию.

Ассет хранит настройку, общую для всех запусков на контуре. То, что меняется от запуска к запуску, передавайте [входным параметром](#config-07-используйте-входные-параметры-робота-только-для-значений-запуска).

## CONFIG-01. Не зашивайте настройки в код

🔴 **Обязательно**

Значение, которое может поменяться без правки логики, храните в ассете: адрес сервера, путь к папке, получателей письма, порог суммы, таймаут. Значение в коде меняют новой версией робота: правка, тест, публикация. Значение в ассете меняют в PIX Master, и робот читает его со следующего запуска.

**Что выносить в ассет:**
- адреса систем и API, строки подключения
- пути к рабочим папкам
- адреса получателей отчетов и поддержки
- пороги и лимиты бизнес-правил: вместо `amount > 10000` ассет `Orders.ProcessOrderRequest.MaxAutoApproveAmount`
- таймауты и число повторов
- пароли и токены, только в защищенных ассетах ([CONFIG-05](#config-05-храните-секреты-в-защищенных-ассетах))

**Что оставить в коде именованной константой.** Значение, которое меняется только вместе с логикой: формат даты, который отдает система (`"dd.MM.yyyy"`), номер столбца в файле без заголовков, текст SQL-запроса с [параметрами](../3-integrations/db.md#db-05-передавайте-значения-в-запросы-только-через-параметры). Константа с именем объясняет, что значит число или строка, а правка по-прежнему в одном месте.

**Индексы.** Не обращайтесь к столбцу или элементу по номеру. Если в таблицу добавят столбец, код возьмет соседний и не заметит ошибки.

```csharp
// Плохо: непонятно, что лежит в столбце 3, и код сломается, если столбцы переставят
var customerName = dataTable.Rows[0][3].ToString();

// Хорошо: столбец по имени
var customerName = dataTable.Rows[0]["CustomerName"].ToString();

// Допустимо, если у источника нет заголовков: именованная константа вместо числа
const int CustomerNameColumnIndex = 3;
var customerName = dataTable.Rows[0][CustomerNameColumnIndex].ToString();
```

## CONFIG-02. Храните настройки в ассетах PIX Master

🔴 **Обязательно**

Настройки робота храните в ассетах PIX Master. Одна сборка робота работает на DEV, UAT и PROD, а значения для каждого контура лежат в мастере. Справочник, который ведет бизнес, робот читает из системы-источника и в ассет не копирует.

**Чем мешает файл настроек рядом с роботом.** Файл раскладывают на каждую машину, и на одной из них остается старое значение. Excel с настройками правят руками, и робот падает на опечатке в ячейке, которую никто не проверил.

**Контуры.** Робот работает с одним мастером на все контуры или со своим мастером на каждом контуре.

![Один мастер на все контуры и свой мастер на каждый контур: имена ассетов и выбор контура](../../images/config/config-contours.png)

| | Один мастер на все контуры | Свой мастер на каждый контур |
|-|----------------------------|------------------------------|
| Когда | Второй мастер дорог или избыточен: MVP, мало роботов | Тестовый и рабочий контуры разделены |
| Имя ассета | С суффиксом контура: `Orders.ProcessOrderRequest.ApiUrl_Prod` | Без суффикса: `Orders.ProcessOrderRequest.ApiUrl` |
| Как робот выбирает значение | Задача передает контур входным параметром `In_Environment`, робот дописывает суффикс к имени ассета ([«Как собрать `config`»](#как-собрать-config-из-ассетов)) | Каждый мастер хранит значения своего контура |
| Где ошибаются | Неверный `In_Environment` направит тестовую задачу в рабочую систему | Новый ассет забывают завести на мастере PROD |

Ассет, общий для всех контуров, суффикса не получает: `Smtp.Server`.

> [!IMPORTANT]
> Заводите ассеты с первого дня разработки. Вынести настройки из готового робота потом дольше, чем сразу положить их в ассеты.

## CONFIG-03. Называйте ассет по уровню, на котором его используют

🔴 **Обязательно**

Ассет называется по самому узкому уровню, на котором его используют: общий, домен, решение или роль ([«Ассеты и очереди»](naming.md#ассеты-и-очереди)). Последняя часть имени говорит, что лежит в ассете: `ApiUrl`, `ReportRecipients`, `MaxAutoApproveAmount`.

- **Контур.** В общем мастере значение, которое зависит от контура, получает суффикс `_Dev`, `_Uat` или `_Prod`: `Orders.ProcessOrderRequest.ApiUrl_Prod`. При своем мастере на каждый контур суффикс не нужен ([CONFIG-02](#config-02-храните-настройки-в-ассетах-pix-master))
- **Учетные данные** называйте по системе, в которую входит робот: `Smtp.Credential`, `Orders.ProcessOrderRequest.Credential1C`
- **Без префиксов типа** вроде `Cred_` или `Param_`: тип ассета мастер показывает в отдельном поле
- **Сложное значение**, например список правил или таблицу соответствий, храните строкой JSON. Отдельного типа для коллекций в PIX Master нет
- **Группа.** В поле «Группа» указывайте домен или решение: `Orders` или `Orders.ProcessOrderRequest`. Тогда ассеты решения лежат в мастере рядом

**Что дает имя по уровню.** По имени видно, кто читает ассет. `Smtp.Server` правят осторожно: его читают все роботы. `Orders.ProcessOrderRequest.ApiUrl` касается одного решения.

## CONFIG-04. Получайте ассеты по ключу

🔴 **Обязательно**

Активности PIX находят ассет по ID или по ключу. Используйте ключ.

ID присваивает мастер. На другом мастере у того же ассета будет другой ID, а в общем мастере `ApiUrl_Dev` и `ApiUrl_Prod` вообще разные ассеты. Робот с ID в коде перестанет находить ассет на другом контуре. Ключ задаете вы, и робот собирает его из имени и суффикса контура ([CONFIG-03](#config-03-называйте-ассет-по-уровню-на-котором-его-используют)). По ключу в коде к тому же видно, какую настройку читает робот.

## CONFIG-05. Храните секреты в защищенных ассетах

🔴 **Обязательно**

Пароли, токены, ключи API и строки подключения с паролем храните в ассетах двух типов. Значение обычного строкового ассета видит каждый, у кого есть доступ к мастеру.

| Тип ассета | Что хранить | Как робот получает |
|------------|-------------|--------------------|
| Учетные данные | Логин и пароль | В момент входа в систему скриптом `PixMaster/GetCredential`. В `config` лежит только имя ассета ([«Как собрать `config`»](#как-собрать-config-из-ассетов)) |
| Защищенные данные | Токен, ключ API, строка подключения с паролем | InitConfig читает в `config`, как обычный ассет |

- Не пишите `config` в лог целиком: защищенные данные лежат в нем открытой строкой. Пишите нужные ключи по одному ([LOG-06](../2-develop/log.md#log-06-не-логируйте-конфиденциальные-данные))
- Не храните секреты в коде, файлах проекта и тестовых данных. Локальные файлы настроек и логи закрывает [`robot.gitignore`](../../templates/robot.gitignore)
- Если секрет попал в Git, сразу смените его в системе и в ассете. Копии репозитория уже есть у других, и чистка истории их не удалит
- Персональные данные клиентов и сотрудников это не настройки. Их робот берет из системы-источника ([PRIVACY-01](../2-develop/privacy.md#privacy-01-обрабатывайте-только-необходимые-персональные-данные))

**Что дает защищенный ассет.** Пароль меняют в ассете, и робота не публикуют заново. Пароль не попадает в историю Git, откуда его уже не убрать.

## CONFIG-06. Храните в `config` только настройки

🟡 **Рекомендуется**

`config` собирается в Init и доходит до каждого скрипта, поэтому в него тянет положить что-то еще: номер текущего заказа, загруженную таблицу, флаг «письмо уже отправлено». Не кладите. Данные транзакции передавайте входными и выходными параметрами скриптов, а состояние робота держите в [переменных `main.pix`](template.md#переменные-mainpix). `config` меняет только Init, один раз за запуск.

**Чем мешают чужие данные в `config`:**
- **Данные переживают транзакцию.** Скрипт положил в `config["OrderNumber"]` номер заказа. Следующая транзакция упала раньше, чем перезаписала ключ, и письмо о сбое ушло с номером прошлого заказа
- **Связь между скриптами не видна.** Скрипт читает ключ, который положил другой скрипт, а по входным параметрам этого не понять. После перестановки вызовов робот падает с `KeyNotFoundException` в неожиданном месте
- **Данные утекают в лог.** `config` пишут в лог при разборе сбоя, и с ним попадают персональные данные клиента

## Как собрать `config` из ассетов

📘 **Справка**

Дополняет [CONFIG-03](#config-03-называйте-ассет-по-уровню-на-котором-его-используют) и [CONFIG-05](#config-05-храните-секреты-в-защищенных-ассетах). Так собирает настройки шаблон из [pix-templates](https://github.com/TheMrDJek/pix-templates). Похоже устроен Config в REFramework: на листе Assets ключ сопоставлен с именем ассета в Orchestrator.

![InitConfig: словари сопоставления, чтение ассетов, словарь config и получение учетных данных](../../images/config/config-init.png)

Скрипт `InitConfig` получает два словаря `string → string`. Ключ в них это имя настройки в роботе, значение это полное имя ассета в PIX Master:
- `In_AssetMapping`: строки, числа, логические значения и защищенные данные. InitConfig читает каждый ассет активностью «Получение данных», проверяет, что значение не пустое, и кладет его в `config` под тем же ключом
- `In_CredentialMapping`: учетные данные. InitConfig их не читает и кладет в `config` только имя ассета

Словари задают во входных параметрах InitConfig в `main.pix`. Суффикс контура дописывают здесь же, у тех ассетов, которые от контура зависят:

```csharp
In_AssetMapping = new Dictionary<string, string>
{
    { "SmtpServer", "Smtp.Server" },
    { "ApiUrl", $"Orders.ProcessOrderRequest.ApiUrl_{In_Environment}" },
    { "ReportRecipients", $"Orders.ProcessOrderRequest.ReportRecipients_{In_Environment}" },
};
In_CredentialMapping = new Dictionary<string, string>
{
    { "Credential1C", $"Orders.ProcessOrderRequest.Credential1C_{In_Environment}" },
};
```

Логин и пароль робот получает в момент входа. `1C/Start1C` вызывает `PixMaster/GetCredential` с именем ассета из `config["Credential1C"]`, и тот возвращает логин и пароль активностью «Получение учетных данных».

После InitConfig запускается `InitApplication`, как InitAllApplications в REFramework. Он проверяет формат значений, доступ к системам и запускает приложения ([TEMPLATE-03](template.md#template-03-проверяйте-в-init-настройки-и-доступ-ко-всем-системам-робота)).

**Почему все значения строки.** «Получение данных» возвращает строку для ассета любого типа. Число или дату скрипт преобразует там, где они нужны, а формат InitApplication проверяет заранее.

**Плюсы:**
- Полное имя ассета записано в одном месте. Переименовали ассет в мастере, поправили одну строку во входных параметрах InitConfig, а скрипты по-прежнему читают `config["ApiUrl"]`
- Все настройки робота видны в одном месте. По входным параметрам InitConfig понятно, какие ассеты завести на новом контуре
- Ассеты читает один цикл в InitConfig, а не активность «Получение данных» в каждом скрипте
- Логин и пароль не лежат в `config` и не попадут в лог вместе с ним

**Минусы:**
- Опечатку в ключе (`config["ApiUlr"]`) компилятор не поймает: робот упадет с `KeyNotFoundException`, когда дойдет до этой строки. Копируйте ключи из входных параметров InitConfig
- Защищенные данные лежат в `config` открытой строкой, поэтому `config` нельзя писать в лог целиком ([CONFIG-05](#config-05-храните-секреты-в-защищенных-ассетах))

## CONFIG-07. Используйте входные параметры робота только для значений запуска

🔴 **Обязательно**

Входные параметры робота задает **запуск**, и они могут отличаться от запуска к запуску: дата отчета, идентификатор процесса, режим работы, размер порции. Не добавляйте во входные параметры рабочие переменные робота и настройки, которые не меняются между запусками.

| Куда | Что | Пример |
|------|-----|--------|
| Входной параметр | Значение, которое задает запуск или задача | `In_ReportDate`, `In_BatchSize`, `In_RunMode`, `In_Environment` |
| Ассет | Настройка, одинаковая для всех запусков на контуре | адрес API, путь к папке, получатели отчета, таймауты |
| Защищенный ассет | Секрет ([CONFIG-05](#config-05-храните-секреты-в-защищенных-ассетах)) | пароли, токены |
| Переменная робота | Промежуточное значение внутри запуска | текущая транзакция, счетчик ошибок, загруженная таблица |

**Чем мешают лишние входные параметры:**
- Каждый входной параметр администратор заполняет или проверяет при настройке задачи. Лишний параметр означает лишнюю ошибку при запуске
- Входной параметр становится частью контракта робота: его уже нельзя переименовать или удалить, не меняя задачи в мастере
- Настройка во входных параметрах повторяется в каждой задаче, и значения расходятся. В ассете настройка одна

**Как оформлять:**
- Все входные параметры имеют тип `string`: проверяйте и преобразуйте их в Init. Если значение некорректно, робот завершает запуск с понятным сообщением
- Для каждого параметра определите значение по умолчанию или явно сделайте его обязательным
- Начинайте имя входного параметра [с префикса `In_`](../2-develop/variable.md#variable-01-используйте-pascalcasing-для-параметров-скриптов)
