# pix-conventions

Соглашения для разработчиков роботов на PIX RPA — от создания проекта до работы робота в PIX Master. Репозиторий — только документация на русском языке (Markdown), кода роботов здесь нет.

## Границы репозитория

Здесь — только то, что нужно разработчику для создания и запуска робота, включая приемы написания кода на C#. Организационные вопросы сюда не входят: работа в команде, Git и код-ревью, жизненный цикл робота (оценка, ТЗ/ТП, приемка, сопровождение), документирование, разработка своих библиотек и активностей. Эти темы будут в отдельных репозиториях. Пока их нет, README называет их текстом в разделе «Что сюда не входит», без ссылок: не придумывай адреса репозиториев. Администрирование PIX Master (машины, мониторинг, права) пока не входит, решение открыто: робот может работать и без мастера (очередь вопросов `PLAN.md`).

## Структура

Разделы идут по пути разработчика:

- `docs/1-project/` — создание проекта: выбор шаблона, шаблон на State Machine, именование проекта/папок/скриптов, конфигурация
- `docs/2-develop/` — разработка: код и активности, имена переменных, условия, циклы, строки, LINQ, файлы, исключения, логи, надежность, ПДн, UI, ИИ, тесты
- `docs/3-integrations/` — очереди, БД, внешние системы, почта, Excel
- `docs/4-master/` — публикация и работа робота в PIX Master
- `docs/checklist.md` — чек-лист разработчика и ревьюера
- `docs/rules-index.md` — реестр правил, **генерируется**, вручную не править
- `docs/glossary.md` — глоссарий
- `templates/robot.gitignore`, `tools/` (`export_diagrams.py` выгружает PNG схем из `images/diagrams.drawio`)
- `.claude/skills/stop-slop/` — навык стиля текста (адаптация stop-slop, MIT)
- `images/<имя файла раздела>/` — скриншоты и схемы: картинки для `error.md` лежат в `images/error/`

## После любой правки в docs/

```bash
python tools/build_docs.py    # пересобирает «Содержание», реестр, проверяет уровни и теги
python tools/check_links.py   # должно быть «Битых ссылок: 0»
```

CI (`.github/workflows/docs.yml`) запускает `build_docs.py --check` и `check_links.py`. Блок `## Содержание` генерируется, не правьте его руками.

## Формат правила

```markdown
## ERROR-04. Указывайте источник исключения

🔴 **Обязательно**

Что делать и почему. Пример «плохо / хорошо», таблица или список.

[⬆ К содержанию](#содержание)
```

- **Тег = имя файла** заглавными: правила `error.md` — `ERROR-NN`. `build_docs.py` падает, если тег не совпадает
- Номер — следующий свободный в файле. **Номера не переиспользуются и не перенумеровываются** после выхода версии; до релиза 2.0 перенумерация допустима по явному решению автора
- Уровни: `🔴 **Обязательно**`, `🟡 **Рекомендуется**`, `🟢 **По ситуации**` — строкой сразу под заголовком
- Заголовок — действие в повелительном наклонении; каждое правило объясняет «почему»
- Ссылки на правила — по тегу с якорем: `[ERROR-03](error.md#error-03-...)`
- Примечания — GitHub alerts (`> [!NOTE]`, `> [!IMPORTANT]`, `> [!WARNING]`, `> [!CAUTION]`); незавершенное — `> [!NOTE]` + `> 🚧 **Раздел в работе.**`
- Примеры — **скриншоты из PIX Studio** (правила оформления — в `CONTRIBUTING.md`, раздел «Примеры: скриншоты из PIX Studio»). C#-вставки (` ```csharp `) постепенно заменяются скриншотами. Скриншоты не придумывай и не генерируй: попроси автора сделать их в Studio и оставь C#-пример до замены
- Справочные разделы без правила — заголовок `##` без тега и строка `📘 **Справка**` под ним на месте уровня; `build_docs.py` ставит «(📘 Справка)» в «Содержание»
- Порядок разделов в файле: 🔴, затем 🟡 и 🟢, справки в конце. До релиза 2.0 после пересортировки правила перенумеровываются по порядку, после релиза новое правило встает в конец своей группы со следующим свободным номером. `build_docs.py` выводит предупреждение, если порядок нарушен
- Новый файл = новый тег: одно короткое английское слово в единственном числе; добавить в карту разделов `README.md`

## Стиль текста

- Правила стиля — в `CONTRIBUTING.md`, раздел «Стиль текста»; полная версия лежит в навыке `.claude/skills/stop-slop/`. Загружай навык перед тем, как писать или править текст в репозитории, и проверяй по нему все, что пишешь, включая коммиты
- Коротко: что сделать, почему, пример. Без канцелярита, общих списков преимуществ, анонсов и лозунгов
- Тире только там, где его требует грамматика, и даже там сначала попробуй перестроить фразу; не склеивай им части фразы. Автор замечает лишние тире как признак нейрослопа
- Термины — по `docs/glossary.md`; новые термины добавлять туда

## Принятые решения

Не пересматривать без явного запроса автора. Новое решение — дописать сюда.

- Целевая версия — **PIX Studio 3.2.1 и выше, .NET 10**: описывай активности и возможности этой версии; возможности C# и .NET новее .NET Framework доступны, оговорки «доступно с версии …» не нужны
- Репозиторий — для разработчиков; организационные вопросы в соглашения не входят
- C# и активности не разделяются: правила разработки одни для C#-кода и скриптов PIX, все лежат в `docs/2-develop/` без подпапок
- Параметры скриптов: префикс направления строчными `in_`, `out_`, `io_`, имя после него в PascalCase (`in_Environment`, `out_Config`) (VARIABLE-01)
- Именование разделено: проект/папки/скрипты/файлы — `1-project/naming.md` (NAMING), параметры и переменные — `2-develop/variable.md` (VARIABLE)
- Тег правила = имя файла; уровни — русские слова с цветом, без MUST/SHOULD/MAY
- Контуры везде называются **DEV / UAT / PROD** (+ TRAIN для машин)
- Excel — **без Interop/COM** (EXCEL-01); почта — **без Outlook COM**, только SMTP/IMAP, EWS (локальный Exchange), Graph (Microsoft 365) (MAIL-01)
- HTTP — через `HttpClient` (INTEGRATION-05), один экземпляр на запуск робота, создается в Init, не в цикле (INTEGRATION-03, 🔴)
- Создание проекта разделено до релиза 2.0: `project.md` «Проект робота» (PROJECT) — правила для любого робота: 01 выбор шаблона по типу процесса, 02 ресурсы робота в проекте, 03 библиотека; `template.md` «Шаблоны роботов на State Machine» (TEMPLATE) — 01 скрипты по папкам по роли, 02 состояния и main.pix. Шаблон работает и без PIX Master
- Архитектурные подходы (Dispatcher / Performer, Transaction Script) — справочные разделы без тега и уровня, а не правила: это варианты, а не требования
- Собственные библиотеки можно использовать, подключение согласуется с тимлидом или ревьюером (PROJECT-03 «Согласуйте подключение собственной библиотеки», 🔴). Сначала проверить, не хватит ли примера скрипта из pix-templates, скопированного в робот: правило про собственные библиотеки (команды, другого отдела, подрядчика), публичные пакеты nuget.org в него не входят; выносить в библиотеку стабильный код, который уже нужен нескольким роботам; бизнес-логику можно, если правило общее для всех процессов и меняется для всех сразу (расчет НДС, ставка в ассете), правило отдельного процесса остается в `States` робота (скидка); подключать конкретную версию
- Ошибки делятся на **бизнес-** и **технические** исключения (ERROR-03); бизнес-исключение помечается `ex.Data["ExceptionType"] = "Business"`, если нельзя создать свой тип; логируется уровнем WARNING
- Сообщение исключения начинается с `[Система] Операция:`, место в коде — в `ex.Data["Source"]` (ERROR-04)
- SQL — только параметры, никакой интерполяции (DB-02)
- Сервер, на котором работают роботы, называется **машиной**, как в PIX Master; «хост» и «сервер робота» — только синонимы в глоссарии
- Именование компонентов PIX Master — по таблице «Общий формат имен» в `docs/4-master/master.md`
- Имена: проект и задача называются `{Домен}.{Решение}`, у связки роботов третья часть `{Роль}` (`Finance.ProcessInvoices.Dispatcher`); домен всегда из одной части, точка разделяет уровни (NAMING-01). Ассет и очередь называются по самому узкому уровню, на котором их используют: общий (`Smtp.Server`, `Rpa.SupportEmails`), домен, решение, роль. «Решение» как solution в C#: один робот или связка роботов; слово «процесс» занято процессом мастера. Репозиторий Git может хранить несколько проектов (домен или решение), как делить, решает команда; папка проекта в репозитории называется как проект `_` только перед суффиксом контура в ассетах и очередях (`_Dev`, `_Uat`, `_Prod`) и в именах тестов (TEST-05); остальные имена из латиницы и цифр в PascalCase (NAMING-04). Скрипт называется как метод, имя понятно без пути, повтор имени папки допустим (NAMING-03)
- Схемы — картинки, без mermaid: исходник всех схем `images/diagrams.drawio`, лист на схему, PNG выгружается в `images/<раздел>/` командой `python tools/export_diagrams.py` (нужен draw.io Desktop). Цвета и оформление — в `CONTRIBUTING.md`, раздел «Схемы»
- Конфигурация (config.md): описаны оба варианта, один мастер на все контуры (суффикс `_Dev`/`_Uat`/`_Prod`, контур задает входной параметр `in_Environment`) и свой мастер на каждый контур. `config` собирает `InitConfig` из словарей `in_AssetMapping` и `in_CredentialMapping` (ключ в роботе → полное имя ассета), проверяет только заполненность; формат и доступы проверяет `InitApplication`. Учетные данные в `config` лежат именем ассета, логин и пароль берет `PixMaster/GetCredential` в момент входа; защищенные данные читаются в `config` как строки. Словарь `string → string`: активности PIX возвращают строки. Ключ в `config` по последней части имени ассета (CONFIG-03). В `config` только настройки (CONFIG-07). Входные параметры задачи несут то, чем одна задача отличается от другой: контур, очередь, число повторов (CONFIG-06). Робот без мастера не расписывается: только пометка, что источник настроек выбирают отдельно
- PIX Master для робота — внешняя система: работа с ним, как с 1С или почтой, лежит в `Infrastructure/PixMaster`
- Готовые шаблоны и примеры часто встречающихся скриптов лежат в репозитории [pix-templates](https://github.com/TheMrDJek/pix-templates); project.md ссылается на них без оговорок, своего каталога шаблонов в соглашении нет. Соглашение описывает итоговую версию, шаблоны приводятся к нему после ревью раздела «Создание проекта»
- Заголовок README: «Соглашения и практики разработки роботов PIX RPA»
- Три формы текста. **Правило** (тег и уровень) фиксирует выбор команды, который ревьюер проверяет по коду. **Справка** (раздел без тега) описывает подход с плюсами и минусами, выбор за командой. **pix-templates** хранит готовые шаблоны и примеры кода. Соглашение отвечает на «что» и «почему», справка помогает выбрать, pix-templates показывает «как». Справку держать рядом с правилом своей темы, отдельный раздел советов не заводить. Проверка нового пункта: можно ли проверить на ревью и есть ли у команды один правильный выбор; если нет, это справка или 🟢
- Концепция соглашения записана в README, раздел «Зачем это нужно»: пять целей по одной фразе (быстрый вход в проект, понятные ошибки, устойчивость к сбоям, независимость от окружения, простые изменения) и таблица ситуаций «без соглашения / по соглашению» со ссылками на правила. Цели верны для любого робота, с очередью или без: механизмы (очереди, повторы, оповещения) описывают правила, а не концепция

## Как вести работу

- **Текущий план — `PLAN.md`.** Сначала проход по разделам сверху вниз (этап 1), потом закрытие очереди вопросов по меткам (этап 2). Статус файла в плане: `[ ]`, `[~]`, `[x]`
- **Вычитку автор делает сам:** идет по файлам и присылает, что поправить или убрать. На каждое примечание сначала дай короткую оценку: как это согласуется с практикой RPA-сообщества (REFramework UiPath, Blue Prism, Automation Anywhere, PIX) и стоит ли пункт отдельного правила (✅ / ⚠️ / ❌ с одной-двумя фразами почему). Затем вноси правку точечно, не переписывай остальной текст файла
- **Не останавливай проход на вопросах.** Если правку нельзя закончить без сверки с PIX, решения автора, скриншота или ИБ, запиши вопрос в «Очередь вопросов» `PLAN.md` с меткой (`PIX`, `РЕШЕНИЕ`, `УРОВЕНЬ`, `АКТУАЛЬНО`, `ИБ`, `СКРИН`, `🚧`) и переходи к следующему примечанию

- Ветка `docsv2` — интеграционная ветка версии 2.0. Проход по разделам идет в рабочей ветке, по коммиту на файл. Каждый пройденный блок плана сливается в `docsv2` перемоткой и пушем без PR (пишет в репозиторий только автор), затем следующий блок начинается от обновленной `docsv2`
- Коммиты на русском в формате `docs: ...`; исправленные issue — `Closes #N` в теле коммита
- **Не добавлять в коммиты и PR строки соавторства** (`Co-Authored-By`, «Generated with Claude Code»): автор коммитов — только владелец репозитория
- Каждое изменение в docs/ — запись в `CHANGELOG.md`, раздел «Не выпущено»
- Не выдумывать возможности PIX RPA и PIX Master: если не уверен в названии активности или настройки — писать обобщенно и спросить автора
