# Как предложить изменение

Соглашения развиваются вместе с практикой команды. Если правило устарело, вызывает споры на ревью или чего-то не хватает, предложите изменение.

## Issue или Pull Request

- **Issue.** Если нужно обсуждение: новое правило, изменение уровня обязательности, спорная формулировка. Используйте шаблон «Предложение правила».
- **Pull Request.** Если изменение очевидное: опечатка, битая ссылка, дополнительный пример к существующему правилу.

## Что сюда относится

В этом репозитории собрано только то, что нужно разработчику робота: от создания проекта до работы робота в PIX Master. Правила разработки одни для C#-кода и для скриптов PIX. Работа команды, Git, процессы, документы и администрирование PIX Master сюда не относятся.

## Формат правила

Каждое правило оформляется заголовком второго уровня в файле раздела:

```markdown
## ERROR-07. Указывайте источник исключения

🔴 **Обязательно**

Одно-два предложения: что делать и почему.

Пример кода «плохо / хорошо», таблица или список правил.

[⬆ К содержанию](#содержание)
```

**Требования:**
- Заголовок пишите как действие в повелительном наклонении: «Используйте…», «Не используйте…», «Проверяйте…»
- **Тег = имя файла** заглавными буквами, номер берите следующий свободный в файле: правила в `error.md` называются `ERROR-01`, `ERROR-02`… Номера не переиспользуются: если правило удалено, его номер больше не занимается
- Новый файл получает новый тег. Называйте файл одним коротким английским словом в единственном числе (`queue.md`, `mail.md`)
- Уровень пишите строкой сразу под заголовком: `🔴 **Обязательно**`, `🟡 **Рекомендуется**` или `🟢 **По ситуации**` (см. [уровни обязательности](README.md#уровни-обязательности))
- Правило объясняет **почему**, а не только **что**
- Примеры по возможности давайте скриншотами из PIX Studio (см. [ниже](#примеры-скриншоты-из-pix-studio))
- На другие правила ссылайтесь по тегу: `[ERROR-03](error.md#error-03-...)`
- Примечания и предупреждения оформляйте как [GitHub alerts](https://docs.github.com/ru/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts): `> [!NOTE]`, `> [!IMPORTANT]`, `> [!WARNING]`
- Незавершенные правила помечаются плашкой `> [!NOTE]` + `> 🚧 **Раздел в работе.**`

## Примеры: скриншоты из PIX Studio

Соглашения читают в первую очередь новые коллеги. Им нужно увидеть, как правило выглядит в PIX Studio: в активности, свойстве, скрипте. Блок кода на C# такого представления не дает: непонятно, в какую активность его вставлять и как это выглядит на схеме процесса. Поэтому основной пример к правилу делается скриншотом из PIX Studio.

**Правила для примеров:**
- **Новое правило.** С примером-скриншотом из PIX Studio. Если правило показывает «плохо / хорошо», нужны два скриншота
- **Существующие C#-вставки** постепенно заменяются скриншотами. Найти оставшиеся можно поиском по ` ```csharp ` в папке `docs/`
- **Код можно оставить под скриншотом**, если его нужно копировать целиком (шаблон запроса, вспомогательный метод). Тогда скриншот показывает, где этот код находится в Studio, а блок кода дает сам текст
- **Только C#** допустим для примеров, которые не привязаны к Studio: сигнатуры методов .NET, шаблоны строк, SQL

**Как оформлять скриншоты:**
- Файл кладите в `images/<имя файла раздела>/`: картинки для `error.md` лежат в `images/error/`
- Имя файла пишите латиницей, по смыслу: `ERROR-03-bad.png`, `ERROR-03-good.png`
- Обрезайте скриншот до нужной области: активность, панель свойств, фрагмент схемы, а не весь экран
- Подпись (alt-текст) описывает, что на скриншоте: `![Активность «Выполнить» с проверкой через TryParse](...)`
- На скриншоте не должно быть паролей, токенов, реальных адресов серверов и персональных данных (см. [PRIVACY-02](docs/2-develop/privacy.md#privacy-02-не-допускайте-персональные-данные-в-логи-статусы-и-имена-файлов)): используйте тестовый проект с вымышленными данными
- Если текст на скриншоте важен для понимания (имя переменной, выражение), продублируйте его в тексте правила: текст на картинке не находится поиском

## Схемы

Схемы архитектуры, переходов и связей между компонентами рисуются в draw.io, а не блоком mermaid. Mermaid сам расставляет блоки, и на схеме из десятка узлов стрелки пересекаются, а подписи наезжают друг на друга.

**Файлы:**
- Исходник всех схем один: [`images/diagrams.drawio`](images/diagrams.drawio), одна схема на листе. Открывается в draw.io Desktop или в плагине Draw.io Integration для VS Code
- Имя листа задает, куда выгружается картинка: лист `template / TEMPLATE-02-states` уходит в `images/template/TEMPLATE-02-states.png`. В документ вставляется PNG
- Правьте только `.drawio`. PNG пересобирается командой `python tools/export_diagrams.py` (все листы) или `python tools/export_diagrams.py template` (листы, чье имя начинается с этой строки). Нужен draw.io Desktop. PNG руками не правьте: следующая выгрузка его перезапишет
- Новую схему рисуйте на новом листе того же файла. Имя файла начинается с тега правила: `TEMPLATE-02-states`. Для справочного раздела без тега имя начинается с имени файла раздела: `project-domain`, `master-components`
- Ширина листа не больше 880 px: так схема помещается в колонку GitHub и на страницу A4 без уменьшения подписей

**Оформление** в классическом стиле draw.io:
- Фон белый, шрифт Helvetica, прямые углы, линии толщиной 1
- В блоке жирное название и одна-две строки деталей мельче: папка, скрипт, технология
- Крупные зоны (проект, домен, этап) рисуются контуром со светлой заливкой и заголовком заглавными буквами. Папку или файл внутри контура (`main.pix`, `Infrastructure`) обводите серым пунктиром с подписью сверху
- Пояснения пишите синим текстом внутри контура
- Внизу каждого листа легенда. Штамп с версией и датой не нужен: их хранит история Git
- Имена на схеме совпадают с текстом и примерами правила. Изменили имя в тексте, поменяйте и схему
- Сплошная стрелка означает «вызывает» или «передает», пунктир означает «использует» или «проверяет», красный пунктир означает переход после ошибки
- Если ветвей много, рисуйте основной путь, а остальные переходы вынесите в таблицу рядом. Так сделано с ошибками и повторами в [TEMPLATE-02](docs/1-project/template.md#template-02-выполняйте-в-каждом-состоянии-только-его-работу)

Цвет обозначает тип блока и одинаков на всех схемах. Цвета взяты из стандартной палитры draw.io:

| Блок | Заливка | Рамка |
|------|---------|-------|
| Робот, состояние, `main.pix` | `#DAE8FC` | `#6C8EBF` |
| Бизнес-логика: `States`, сценарий транзакции и его шаги | `#FFF2CC` | `#D6B656` |
| Адаптер `Infrastructure` | `#D5E8D4` | `#82B366` |
| PIX Master: задача, ассет (шестиугольник), очередь (лежачий цилиндр), элемент очереди | `#E1D5E7` | `#9673A6` |
| Триггер, расписание (скругленный) | `#FFE6CC` | `#D79B00` |
| Наш компонент: `Helpers`, `Common`; `Tests` (пунктир) | `#F5F5F5` | `#666666` |
| Внешняя система, источник данных (скругленный) | `#FFFFFF` | `#666666` |
| Исключение, переход после ошибки (красный пунктир) | `#F8CECC` | `#B85450` |

| Контур | Заливка | Рамка |

## Стиль текста

Правила основаны на [stop-slop](https://github.com/hardikpandya/stop-slop) и адаптированы к русскому языку, полная версия лежит в навыке `.claude/skills/stop-slop/`. Цель: текст, который читается быстро и не звучит как сгенерированный.

**Пишите коротко.** Правило состоит из того, что сделать, почему и примера. Если без предложения правило понятно, вычеркните его.

**Называйте конкретное.** Вместо «повышает надежность» напишите, что сломается: «робот не найдет ассет после переноса на UAT». Не пишите списки преимуществ из общих слов: «гибкость», «масштабируемость», «улучшенная читаемость».

**Указывайте, кто действует.** «Робот читает ассет в Init», а не «ассет считывается в Init». «Разработчик задает ключ», а не «ключ задается».

**Убирайте пустые слова:**

| Не пишите | Как исправить |
|-----------|---------------|
| является, осуществляет, производит, данный | Глагол действия: «робот читает», «этот файл» |
| позволяет, обеспечивает, способствует | Что именно происходит: «робот перезапускает приложение» |
| ключевой, эффективный, критически важный, существенно, значительно | Удалить или заменить фактом |
| очень, крайне, действительно, просто, на самом деле | Удалить |
| важно отметить, стоит отметить, следует учитывать | Удалить, сразу писать суть |
| в рамках, с целью, в случае если | в, чтобы, если |

**Не стройте фразы по шаблону:**
- «Не X, а Y». Пишите сразу Y.
- Три пункта ради ритма. Если пунктов два, пишите два.
- Вывод-лозунг в конце абзаца («Это залог стабильности»). Удалите его.
- Анонсы («Рассмотрим», «В этом разделе мы…»). Начинайте с сути.

**Тире.** Тире сильнее всего выдает сгенерированный текст, поэтому ставьте его только там, где его требует грамматика: «Ассет — параметр робота». Не склеивайте им части фразы вместо точки, двоеточия или запятой. Даже грамматическое тире сначала попробуйте убрать перестройкой фразы: «Имена папок задает NAMING-02» вместо «Имена папок — по NAMING-02», «**Масштабирование.** Несколько обработчиков…» вместо «**Масштабирование** — несколько обработчиков…». Если в абзаце больше одного тире, перепишите абзац.

**Навык для Claude Code.** Подробные правила с примерами лежат в `.claude/skills/stop-slop/`. Claude Code подхватывает навык сам, когда пишет текст в этом репозитории. Человеку он пригодится как расширенный чек-лист.

## Перед отправкой Pull Request

Пересоберите содержание файлов и реестр правил, затем проверьте ссылки:

```bash
python tools/build_docs.py
python tools/check_links.py
```

`build_docs.py` также проверяет, что у каждого правила есть уровень и тег совпадает с именем файла. Эти же проверки выполняются в CI. Реестр [docs/rules-index.md](docs/rules-index.md) генерируется автоматически, не редактируйте его вручную.

Добавьте запись в [CHANGELOG.md](CHANGELOG.md) в раздел «Не выпущено».

Пишите коммиты на русском в формате `docs: ...`. Не добавляйте в коммиты и описание PR строки соавторства: `Co-Authored-By`, «Generated with Claude Code» и подобные подписи ИИ-ассистентов. Автор изменения тот, кто отправляет коммит.

## Изменение существующих правил

- Смена уровня на более строгий (🟡 → 🔴) или удаление правила обсуждается в Issue до PR
- Если меняется смысл правила, укажите это в CHANGELOG: команды могли ссылаться на старую формулировку
- Если меняется заголовок, меняется и якорь: проверьте ссылки через `tools/check_links.py`
