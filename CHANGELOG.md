### Изменено
- template.md, project.md: переход между состояниями называется как активность PIX Studio, «Перейти на шаг», вместо `GoToStep`; названа и вторая активность, «Условный переход к шагу», со ссылками на документацию PIX. Из TEMPLATE-02 убрана таблица блоков `Init` / `Init - Route`: ее заменило одно предложение в разделе «main.pix»
- TEMPLATE-02 «Выполняйте в каждом состоянии только его работу» (было «Используйте состояния State Machine по назначению») переписан по состояниям: классический шаблон из четырех состояний с повторами и зачем повторы при работе с интерфейсом; `main.pix` как точка входа и обертка над слоями с блоками `Route`; Init собирает настройки, запускает приложения, проверяет доступ, собирает коллекцию транзакций не из очереди, при повторе перезапускает приложение; Get Transaction только берет элемент и догружает данные, папка `GetTransaction` вместо `GetSetTransaction`; Process Transaction доводит транзакцию до конца, включая статус и ответ, `Route` помечает исключения и выбирает переход, кроме обработки пачками; End Process очищает окружение, пометка о том, когда приложение лучше не закрывать
- TEMPLATE-03 «Проверяйте в Init настройки и доступ ко всем системам робота»: добавлена проверка ассетов (заполнены, верный формат адресов, дат и чисел); ошибка в настройке не повторяется, робот сразу пишет поддержке
- TEMPLATE-01 переименован: «Раскладывайте скрипты по папкам по роли» вместо «Разделяйте проект на слои». Ссылки и карта разделов README обновлены
- template.md называется «Шаблоны роботов на State Machine» и описывает, как обычно устроены шаблоны команды, без ссылки на шаблон PIX Studio; из справки «Плюсы и минусы State Machine» в project.md «Универсальный шаблон» тоже убран. Вступление объясняет, что схемы, дерево папок и таблицы файла показывают одного робота `Orders.ProcessOrderRequest`. TEMPLATE-01 проводит границу между `States` и `Infrastructure`: адаптер отвечает «как сделать в системе», сценарий «что и когда делать»; любое действие в интерфейсе или API системы лежит в `Infrastructure`, даже разовое. Справка о сценарии разбирает `AddOrderItem` по шагам таблицей и схемой: адаптеры открывают заказ, получают остаток, добавляют строку и проводят заказ, сценарий проверяет результат и выбрасывает бизнес-исключения. Робот из примера не пишет статус в БД: ответ чат-боту уходит в очередь ответов, статус заявки хранит элемент входной очереди. Из TEMPLATE-03 убрана проверка БД, пример в «Почему» переведен на очередь ответов. TEMPLATE-02 начинается с оговорки: состояний бывает три, пять или десять, правило описывает типовой шаблон из четырех состояний (REFramework и аналоги), а для других шаблонов действует тот же принцип
- TEMPLATE-01 описывает слои по назначению кода: переходы, бизнес-логика, адаптеры внешних систем, универсальные скрипты. `Helpers` это универсальные скрипты, не привязанные к состоянию или системе, чаще всего чистые функции. Правило начинается с идеи: не складывать скрипты одной кучей в корень проекта; переходы остаются в `main.pix`, по папкам раскладываются скрипты. Таблица слоев заменена списком «папка: роль», матрица вызовов одной фразой, дерево проекта сокращено до слоев, таблица «Куда положить скрипт» одной фразой. Сокращение ШАР убрано. В TEMPLATE-02 ответ и статус элемента пишет `CompleteTransaction`, его вызывает блок `Route`. Короткое состояние, до 1–5 строк кода, остается в блоке `main.pix` без папки; End Process обычно остается контейнером в `main.pix` без отдельного скрипта и try/catch, сложное завершение выносится в `States/EndProcess` (имя папки в NAMING-02).
